The single most useful interview skill is **pattern recognition** — reading a problem in 30 seconds and immediately knowing which family of solutions to reach for. This page is a cheat sheet.

## Interview-ready explanation

Pattern recognition means mapping a problem's input shape, constraints, and wording to the algorithm family that solves it, before writing any code. First I check the constraints to get a complexity budget. Then I look for trigger phrases: sorted input plus a pair or triplet points to two pointers, a contiguous subarray with a property points to sliding window, a shortest path with unweighted edges points to BFS, "top K" points to a heap, and "count the ways" or "minimum operations" points to DP. If nothing matches, I state the brute force with its complexity, find the work it repeats, and remove that repetition with a cache (DP) or a better data structure (hash map, heap).

**One-liner:** Read the constraints for a complexity budget, match trigger phrases to a pattern, and if nothing fits, optimize the brute force by removing its repeated work.

## Two-question filter

When you see a problem, ask:

1. **Is the input sorted / can it be sorted?** → Binary search, two pointers, greedy on intervals.
2. **What kind of output is asked for?** → A count or an optimum (min/max) → DP, greedy, or a heap. Every solution generated → backtracking. Yes/no (reachable? possible?) → DFS / BFS / DP.

## Common red flags

- **"All permutations / combinations of ..."** but with non-trivial n → backtracking is exponential by nature; check constraints.
- **n or values "on the order of 10⁹"** → you cannot touch every value, so aim for O(log n), O(√n) or O(1); think binary search on the answer or math. If instead there are many queries over an array, aim for O(1) or O(log n) per query with precomputation (prefix sums, hashing).
- **"Cyclic / circular"** → trick is often to *concatenate the array with itself* and do a linear pass.
- **"K matters"** → heap of size K → O(n log K) is the usual win.

## When you don't recognize anything

Fall back to the **brute force**:

1. State the brute force out loud, get its complexity, **agree it's too slow**.
2. Identify *what work is repeated* in the brute force. That's almost always the entry point — caching it leads to DP/memoization; eliminating it via a smart data structure leads to a heap or hash.
3. Ask the interviewer: *"Are duplicates allowed? Negatives? What's the range of n?"* — constraints shape the algorithm.
