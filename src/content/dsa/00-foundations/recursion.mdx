## Interview-ready explanation

Recursion solves a problem by having a function call itself on a smaller version of the same problem, until it reaches a base case it can answer directly. Every recursive solution needs two things: a base case that stops the calls, and a recursive case that shrinks the input and combines the sub-results. Each call takes a stack frame, so recursion costs O(depth) extra space, and very deep recursion can overflow the stack. When the same subproblems repeat, as in Fibonacci, I memoize them, which turns exponential time into polynomial time; that is top-down dynamic programming.

**One-liner:** Recursion reduces a problem to smaller copies of itself until a base case, using O(depth) stack space, and memoization removes repeated subproblems.

## The shape

A recursive function solves a problem by:

1. **Base case** — a small input it can answer directly (no recursion).
2. **Recursive case** — reduce the problem to a smaller version of itself, then combine.

Miss the base case → infinite recursion → stack overflow. Miss the reduction → same.

```python
def factorial(n):
    if n <= 1: return 1        # base case
    return n * factorial(n - 1) # recursive case
```

## The call stack

Each call gets its own frame: local variables, parameters, return address. The stack grows on every call and shrinks on every return. Depth limits are small: Python stops at 1000 frames by default (`RecursionError`), and Java typically overflows somewhere in the low thousands to tens of thousands of frames (`StackOverflowError`), depending on stack size and frame size.

For deep recursion (e.g. tree depth in the millions), convert to an explicit stack iteratively — same complexity, no recursion limit.

## Tail recursion

A function is *tail-recursive* if the recursive call is the last thing it does. Some compilers/runtimes (Scheme, Scala for self-recursive calls, Kotlin with `tailrec`) optimize this into a loop — no stack growth. Python and Java do not, and in JavaScript only Safari's engine implements the ES2015 tail-call rule (V8 in Chrome and Node does not) — so convert to a loop manually.

## Memoization — turn O(2ⁿ) into O(n)

Naïve Fibonacci:

```python
def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)   # recomputes the same subproblems
```

This is O(2ⁿ). Cache the answers:

```python
from functools import lru_cache
@lru_cache
def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)
```

Now O(n) time, O(n) space. Memoization = top-down DP.

## Recursion vs iteration

| Recursion | Iteration |
| --- | --- |
| Natural for trees, graphs, divide-and-conquer | Natural for arrays, fixed loops |
| Easier to write for backtracking | No stack-overflow risk |
| O(depth) stack space | Often O(1) extra space (an explicit stack still costs O(depth)) |
| Slower in practice (function call overhead) | Faster |

In interviews, *prefer the clearer one*. If the interviewer asks for the iterative version, convert it.

## Recurrence relations

A recursive function's runtime obeys a recurrence:

- **Merge sort**: T(n) = 2T(n/2) + O(n) → O(n log n)
- **Binary search**: T(n) = T(n/2) + O(1) → O(log n)
- **Naïve Fibonacci**: T(n) = T(n-1) + T(n-2) + O(1) → O(2ⁿ) (tight bound about 1.618ⁿ, the golden ratio)

The **Master Theorem** solves `T(n) = aT(n/b) + O(n^d)`:

- `a > b^d` → `O(n^(log_b a))`
- `a = b^d` → `O(n^d · log n)`
- `a < b^d` → `O(n^d)`

## Patterns where recursion shines

- **Tree traversal** — recurse on children.
- **Backtracking** — try a choice, recurse, undo.
- **Divide and conquer** — split, recurse, merge.
- **DP top-down** — solve subproblems lazily with memoization.
