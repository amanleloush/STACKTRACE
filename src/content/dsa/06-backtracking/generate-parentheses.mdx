## Problem
Given `n` pairs, generate every well-formed string of `n` open and `n` close parens — e.g. `n=3` produces `["((()))","(()())","(())()","()(())","()()()"]`.

## Interview-ready explanation
This is backtracking with two counters. I build the string one character at a time and track how many opens and closes I've used. I may add `'('` while opens are fewer than n, and `')'` only while closes are fewer than opens, so every prefix stays valid and I never build a bad string. When the length reaches 2n, I save it. The number of results is the n-th Catalan number, about 4ⁿ / (n√n), and each costs O(n) to build, so time is O(4ⁿ / √n) and extra space is O(n) for the recursion and the current string.

**One-liner:** Backtrack adding `(` while open is less than n and `)` while close is less than open, saving each string of length 2n: O(4ⁿ / √n) time, O(n) space.

## Intuition
At every step you have at most two choices: append `'('` or append `')'`. Two simple constraints kill every invalid branch *before* you recurse: you can only open while `open < n`, and you can only close while `close < open`. The **invariant** is that every prefix in `path` is itself a valid (possibly incomplete) parenthesis string — never has more `)` than `(`, never exceeds `n` opens.

## Algorithm
Carry two counters — `open` (so far) and `close` (so far). Two if-branches, both pruning.

```cpp
class Solution {
public:
    vector<string> generateParenthesis(int n) {
        vector<string> res;
        string path;
        dfs(0, 0, n, path, res);
        return res;
    }

private:
    void dfs(int open, int close, int n, string& path, vector<string>& res) {
        if ((int)path.size() == 2 * n) {
            res.push_back(path);
            return;
        }
        if (open < n) {
            path.push_back('('); dfs(open + 1, close, n, path, res); path.pop_back();
        }
        if (close < open) {
            path.push_back(')'); dfs(open, close + 1, n, path, res); path.pop_back();
        }
    }
};
```

```java
class Solution {
    public List<String> generateParenthesis(int n) {
        List<String> res = new ArrayList<>();
        dfs(0, 0, n, new StringBuilder(), res);
        return res;
    }

    private void dfs(int open, int close, int n, StringBuilder path, List<String> res) {
        if (path.length() == 2 * n) {
            res.add(path.toString());
            return;
        }
        if (open < n) {
            path.append('('); dfs(open + 1, close, n, path, res); path.deleteCharAt(path.length() - 1);
        }
        if (close < open) {
            path.append(')'); dfs(open, close + 1, n, path, res); path.deleteCharAt(path.length() - 1);
        }
    }
}
```

def generateParenthesis(n):
    res, path = [], []

    def dfs(open_, close):
        if len(path) == 2 * n:
            res.append("".join(path))
            return
        if open_ < n:
            path.append("("); dfs(open_ + 1, close); path.pop()
        if close < open_:
            path.append(")"); dfs(open_, close + 1); path.pop()

    dfs(0, 0)
    return res

## Walkthrough
The widget runs on `n = 3`:

1. **Root.** `path = ""`, `open = 0`, `close = 0`. `open < 3` so add `'('` → recurse with `"("`, `open = 1`.
2. **Greedy left spine.** Open is still legal twice more → reach `"((("` with `open = 3, close = 0`. Now `open ≥ n` blocks `'('`, but `close < open` lets `')'` fire three times → emit `"((()))"`.
3. **First backtrack.** Pop back to `"(("` (the parent frame's phase advanced past `'('`). Now try `')'` → `"(()"`. Down that subtree: `"(()("` → `"(()()"` → `"(()())"` is recorded; sibling `"(())"` path closes to `"(())()"`.
4. **Mid-tree.** Pop further; from root pick `"()"` first instead. Subtree yields `"()(())"` and `"()()()"` — the open/close counters in the readout flip back and forth.
5. **End.** Five strings emitted: `((())), (()()), (())(), ()(()), ()()()` — the 3rd Catalan number **C₃ = 5**.

## Complexity

- time **O(4ⁿ / √n)** Catalan
- space **O(n)** recursion + path

## Pitfalls
- Generating all `2^(2n)` strings and filtering — about `n^1.5` times more work than the pruned search (`n·4ⁿ` vs `~4ⁿ/√n`); fine for tiny `n`, but it is the answer interviewers push back on.
- Wrong close rule: guarding `')'` with `close < n` instead of `close < open` lets invalid prefixes like `"())"` through. A close is legal only while there is an unmatched open, so compare `close` with `open`, not with `n`.
- Tracking only `total_length` without `open`/`close` — you lose the ability to prune invalid prefixes.
- Returning the `path` list reference (mutable) instead of `"".join(path)` — every result becomes empty.
- Off-by-one: stopping at `len(path) == n` instead of `2 * n`.
