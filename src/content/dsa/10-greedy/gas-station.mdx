## Problem
At station `i` you gain `gas[i]` and pay `cost[i]` to drive to `i+1` (circular). Return the starting index that lets you complete the loop, or `-1`.

## Interview-ready explanation
This is a one-pass greedy over a running fuel balance. There are two facts. First, a valid start exists if and only if total gas is at least total cost. Second, if I start at `s` and my tank goes negative at station `j`, then no station from `s` to `j` can be a valid start, so the next candidate is `j + 1`. So I check the totals, then sweep once, adding `gas[i] - cost[i]` to the tank and resetting the start to `i + 1` with an empty tank whenever it drops below zero. The final candidate is the answer. It runs in O(n) time and O(1) space.

**One-liner:** If total gas covers total cost, sweep once with a running tank and move the start to i + 1 whenever the tank goes negative; the last start is the answer, in O(n) time and O(1) space.

## Intuition
Two facts unlock the O(n) greedy. **First**, a solution exists iff `sum(gas) ≥ sum(cost)` — otherwise no start can possibly work. **Second**, if you start at `i` and run out of gas at `j`, then no station in `[i, j]` can be a valid start: each of those would have arrived at `j` with no more fuel than you did (you reached each of them with a non-negative tank). So you reset the candidate start to `j+1` and keep sweeping. One pass, no backtracking — the key argument is "any failed prefix is forever unusable."

```cpp
class Solution {
public:
    int canCompleteCircuit(vector<int>& gas, vector<int>& cost) {
        int sumGas = 0, sumCost = 0;
        for (int g : gas) sumGas += g;
        for (int c : cost) sumCost += c;
        if (sumGas < sumCost) return -1;
        int tank = 0, start = 0;
        for (int i = 0; i < (int)gas.size(); ++i) {
            tank += gas[i] - cost[i];
            if (tank < 0) {  // i is unreachable from start
                start = i + 1;
                tank = 0;
            }
        }
        return start;
    }
};
```

```python
def can_complete(gas, cost):
    if sum(gas) < sum(cost):
        return -1
    tank, start = 0, 0
    for i in range(len(gas)):
        tank += gas[i] - cost[i]
        if tank < 0:           # i is unreachable from start
            start, tank = i + 1, 0
    return start
```

## Walkthrough
Example: `gas = [1, 2, 3, 4, 5]`, `cost = [3, 4, 5, 1, 2]`.

1. **Init.** `tank = 0`, `total = 0`, `start = 0`. (Total gas 15 = total cost 15 → a solution exists.) The widget keeps a running `total` of every diff instead of the upfront `sum` check in the code; checking `total ≥ 0` at the end is equivalent.
2. **i=0.** `diff = 1 − 3 = −2`. `tank → −2 < 0` → **reset**: `start = 1`, `tank = 0`. `total = −2`.
3. **i=1, i=2.** Same story: `diff = −2` each time → reset `start` to 2, then 3. After `i=2`, `total = −6`, `tank = 0`, `start = 3`.
4. **i=3, i=4.** `diff = 4 − 1 = 3` → `tank = 3`, `total = −3`. Then `diff = 5 − 2 = 3` → `tank = 6`, `total = 0`. No more resets.
5. **End.** Loop ends; `total = 0 ≥ 0` → return `start = 3`. Starting at station **3** lets the trip complete.

time **O(n)** · space **O(1)**

## Pitfalls
- Forgetting the global feasibility check — without it, you might return a "start" that still fails.
- Trying to simulate from every station — O(n²) and unnecessary.
- Resetting `tank` to `gas[i+1] - cost[i+1]` instead of `0` — the next loop iteration adds that diff itself, so you would count it twice.
- Misreading the cost: `cost[i]` is from `i` to `i+1`, not from `i-1` to `i`.
- Assuming uniqueness — the problem guarantees a unique answer when one exists, but writing code that depends on uniqueness can break on variants.
