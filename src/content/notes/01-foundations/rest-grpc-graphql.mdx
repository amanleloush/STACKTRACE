## Definition (interview-ready)

**REST** is an architectural style over HTTP using resource-oriented URLs and standard verbs, typically with JSON payloads. **gRPC** is an RPC framework using Protocol Buffers over HTTP/2 with strongly typed contracts and code generation. **GraphQL** is a query language and runtime where clients describe exactly the data shape they want, executed against a single endpoint.

## Why it matters

The choice between these shapes API ergonomics, mobile bandwidth, internal-service performance, and team coupling for years. "Use REST" is rarely the full answer — most modern systems mix all three (REST/GraphQL at the edge, gRPC internally).

## Core concepts

### REST

- Resources identified by URLs: `/users/42/orders/7`.
- Verbs map to actions: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`.
- Statelessness on the server (no per-client session in the protocol).
- Self-descriptive messages — uses standard HTTP semantics (status codes, caching headers, content negotiation).
- **HATEOAS**: responses include links to related resources. Theoretically pure REST; almost no one does this in practice.
- Payload: typically JSON, sometimes XML.

### gRPC

- Schema-first: define services and messages in **`.proto`** files.
- Code generation: client + server stubs in many languages.
- **Protocol Buffers**: compact binary encoding (much smaller than JSON).
- Runs over **HTTP/2**: multiplexed streams, header compression, trailers (gRPC doesn't use server push).
- Four call types: unary, server streaming, client streaming, bidirectional streaming.
- Built-in: deadlines, cancellation, metadata (headers), interceptors, mTLS.

### GraphQL

- One endpoint (`/graphql`), POST queries.
- Client specifies the exact fields it needs:
  ```graphql
  query { user(id: 42) { name orders(last: 5) { total } } }
  ```
- Strongly typed schema — server publishes types, queries, mutations, subscriptions.
- Solves "over-fetching" (REST returns too much) and "under-fetching" (REST needs N round-trips).
- Tradeoff: server runs an interpreter, complex caching (POST + query body, not URL).

## How it works (the wire)

### REST request
```
GET /users/42 HTTP/1.1
Accept: application/json
```
```json
{ "id": 42, "name": "Aman", "email": "...", "orders": [...] }
```

### gRPC request
Binary protobuf frame over HTTP/2:
```
:method = POST
:path = /user.UserService/GetUser
content-type = application/grpc+proto
grpc-encoding = gzip
<binary protobuf body>
```
Trailers carry `grpc-status`.

### GraphQL request
```
POST /graphql
Content-Type: application/json

{ "query": "{ user(id: 42) { name orders(last: 5) { total } } }" }
```

## Real-world examples

- **Stripe, GitHub, Twilio**: public REST APIs (developer ergonomics, browser-friendly).
- **GitHub also offers GraphQL** for richer queries (`api.github.com/graphql`).
- **Google, Netflix, Square**: gRPC internally between microservices.
- **Shopify, Meta (Facebook)**: GraphQL at the mobile/edge — clients pick exactly what they need to save bandwidth.
- **gRPC-Web**: lets browsers talk to gRPC backends through a proxy. Used when web clients want gRPC's typing.

## Common pitfalls

- **REST + N+1 problem**: client loads a list, then makes N calls to enrich each item. GraphQL or batch endpoints fix this.
- **gRPC through HTTP/1.1 proxies**: silent failure. Confirm every hop supports h2.
- **GraphQL N+1 on the resolver side**: naive resolvers fetch one row at a time. Use **DataLoader** to batch.
- **Versioning**: REST often uses `/v1/`. gRPC uses field numbers (additive evolution) — never reuse a field number. GraphQL is supposed to be additive forever (deprecate, don't remove).
- **Caching**: REST GETs cache trivially (URL is the key). GraphQL is POST → custom caching layer (persisted queries, Apollo client cache).
- **Authorization**: GraphQL exposes broad surface area — easy to leak data through field traversal. Authorize per field, not just per endpoint.
- **gRPC errors**: use `grpc-status` codes (NOT_FOUND, INVALID_ARGUMENT, ...) — there are only 17 (OK plus 16 error codes), and they map well to HTTP if you ever need to bridge.

## When to pick each

| Need | Pick |
|---|---|
| Public API for unknown clients (browsers, curl) | REST |
| Browser/mobile fetching exact shapes, multiple resources at once | GraphQL |
| Internal microservices, low latency, strong typing | gRPC |
| Streaming (server/client/bidi) | gRPC |
| File upload | REST (multipart) |
| Heavy mobile + bandwidth constrained + diverse client needs | GraphQL |
| Need HTTP caching, CDNs | REST |

## Practice questions

<Practice>

<QA q="When is gRPC better than REST?" level="easy">

For internal services where you control both sides and need strong typing, low latency, small payloads, or streaming. gRPC wins on schema enforcement (`.proto` + codegen), Protobuf's compact binary encoding, and HTTP/2 multiplexing. REST stays better for public, browser-facing APIs that benefit from HTTP caching.

</QA>

<QA q="What problem does GraphQL solve?" level="easy">

**Over-fetching** (a REST endpoint returns more than the client needs) and **under-fetching** (the client needs many REST calls to build one screen). In GraphQL the client describes exactly the data shape it needs and gets it from one endpoint in one request.

</QA>

<QA q="What are gRPC's four call types?" level="easy">

1. **Unary**: one request, one response.
2. **Server streaming**: one request, a stream of responses.
3. **Client streaming**: a stream of requests, one response.
4. **Bidirectional streaming**: both sides stream independently over the same HTTP/2 stream.

</QA>

<QA q="What are the core constraints of REST?" level="easy">

Resources are identified by URLs (`/users/42/orders/7`), standard verbs map to actions (GET, POST, PUT, PATCH, DELETE), the server keeps no per-client session state in the protocol, and messages are self-descriptive through standard HTTP semantics (status codes, caching headers, content negotiation). HATEOAS (hypermedia links in responses) is part of pure REST but rarely implemented.

</QA>

<QA q="How do you version a gRPC API?" level="medium">

Evolve additively: add fields with new field numbers, and never reuse or change a field number. When you delete a field, mark its number (and name) `reserved` so nobody reuses it. Proto3 has no `required` (`optional` returned in protobuf 3.15 for explicit field presence). For truly breaking changes, create a new service or package (`v2`) and run both.

</QA>

<QA q="What is the GraphQL N+1 problem and how do you fix it?" level="medium">

A query like `users { posts { title } }` runs one DB query for users and then one per user for posts: N+1 in total. Fix with batching: **DataLoader** collects the keys requested within one tick and issues a single `IN (...)` query, then hands each resolver its results by key.

</QA>

<QA q="Why is GraphQL hard to cache?" level="medium">

REST GETs cache on the URL. GraphQL normally sends a POST with the query in the body, so HTTP and CDN caching don't apply. Options: **persisted queries** (clients send a hash of a registered query, which can be a cacheable GET), normalized client caches (Apollo, Relay), or server-side response caching with cache tags.

</QA>

<QA q="Why is authorization trickier in GraphQL than in REST?" level="medium">

REST exposes a fixed set of endpoints, so you can authorize per route. GraphQL exposes one endpoint over a whole graph that clients can traverse, e.g. `order → customer → paymentMethods`, so a check at the entry point doesn't protect fields reachable through relationships. Authorize **per field/type** in resolvers or the business layer, and limit query depth and cost.

</QA>

<QA q="Compare gRPC streaming with GraphQL subscriptions." level="hard">

gRPC streaming lives at the transport level (HTTP/2 streams): strictly typed, bidirectional, on a persistent connection, a good fit for server-to-server and control-plane traffic. GraphQL subscriptions usually run over WebSockets and let a client (often a browser) subscribe to events the server pushes. Different audiences: gRPC for internal services, subscriptions for live UI updates.

</QA>

<QA q="How would you migrate a REST API to gRPC without breaking clients?" level="scenario">

Run both. Use **grpc-gateway** to generate a REST→gRPC reverse proxy from the `.proto` definitions, so there's a single source of truth and two transports. Move internal clients to gRPC gradually and keep REST for external clients until it can be sunset. Remember every hop must support HTTP/2, since gRPC through an HTTP/1.1 proxy fails silently.

</QA>

<QA q="A team built a GraphQL API for mobile, but p99 latency is bad. What do you investigate?" level="scenario">

1. Resolver N+1: audit with query tracing and add DataLoader.
2. Expensive or abusive queries: enforce max depth and query cost limits.
3. Fan-out across many services behind nested resolvers: consider federation, stitching, or precomputed views.
4. A cold persisted-query cache: preload it.
5. Expensive fields fetched on every query: make them deferrable or move them to a separate query.

</QA>

<QA q="You're designing APIs for a product with a public developer API, a bandwidth-constrained mobile app with many screens, and 40 internal microservices. What do you pick for each?" level="scenario">

- **Public developer API → REST**: browser- and curl-friendly, cacheable GETs, familiar to unknown clients.
- **Mobile app → GraphQL** at the edge: each screen fetches exactly its shape in one round trip, which saves bandwidth. Budget for DataLoader, field-level auth and query-cost limits.
- **Internal services → gRPC**: typed contracts, compact Protobuf, deadlines, cancellation, and streaming.

Mixing all three is normal. The edge and the internal mesh have different needs.

</QA>

</Practice>

## Quiz

<Quiz>

<MCQ q="A mobile screen needs a user, their last 5 orders, and each order's shipment status. Which problem does GraphQL address here compared with plain REST?" options={["Under-fetching, since REST would need several round trips to assemble the screen", "Lack of encryption in REST", "REST's inability to return JSON", "HTTP/2 multiplexing being unavailable to REST"]} answer={0}>

Building the screen from REST resources takes multiple requests (under-fetching), and each may return unneeded fields (over-fetching). GraphQL fetches the exact shape in one request. Encryption and JSON support aren't differences between them.

</MCQ>

<MCQ q="You removed field 4 from a protobuf message. What should you do?" options={["Reuse field number 4 for the next new field", "Renumber the remaining fields to close the gap", "Mark 4 (and the old name) as reserved", "Change the message name"]} answer={2}>

Old clients still interpret number 4 with its old type, so reusing it corrupts data. reserved stops anyone from reusing it. Renumbering breaks wire compatibility for every field.

</MCQ>

<MCQ q="A GraphQL query for 100 users and their posts issues 101 SQL queries. What is the standard fix?" options={["Switch the endpoint from POST to GET", "Add an HTTP cache in front of the server", "Increase the database connection pool", "Batch the per-user lookups with DataLoader into one IN query"]} answer={3}>

This is resolver-side N+1, and DataLoader collapses the per-key lookups into a batched query. A cache or bigger pool only hides the symptom, and the HTTP method has nothing to do with resolver execution.

</MCQ>

<MCQ q="Why don't GraphQL responses benefit from CDN caching by default?" options={["GraphQL responses are binary", "Queries are typically sent as POST bodies, so the URL is not a usable cache key", "GraphQL forbids cache headers", "GraphQL only runs over WebSockets"]} answer={1}>

HTTP caches key on the method and URL, and POST bodies aren't cached. Persisted queries turn a query into a hash that can be sent as a cacheable GET. GraphQL responses are JSON, and subscriptions are only one part of GraphQL.

</MCQ>

<MCQ q="Which gRPC call type fits a client that uploads a large stream of sensor readings and receives one summary at the end?" options={["Unary", "Server streaming", "Client streaming", "Bidirectional streaming"]} answer={2}>

The client sends many messages and the server replies once, which is client streaming. Bidirectional would also work but is unnecessary when the server only answers once.

</MCQ>

<MCQ q="An internal service checks auth only at the GraphQL entry query, yet users can read other customers' payment data through nested fields. What is the right fix?" options={["Authorize at the field or type level as the graph is traversed", "Move to a single REST endpoint", "Disable introspection", "Rate-limit the endpoint"]} answer={0}>

GraphQL lets clients reach data through relationships, so each field or type must enforce access. Disabling introspection hides the schema but doesn't stop a crafted query, and rate limiting doesn't address authorization.

</MCQ>

<MCQ q="You want to offer both REST and gRPC from one set of definitions during a migration. Which approach fits?" options={["Hand-write a REST server and a gRPC server separately", "Use GraphQL federation", "Expose gRPC directly to browsers without a proxy", "Use grpc-gateway to generate a REST reverse proxy from the .proto files"]} answer={3}>

grpc-gateway translates REST/JSON to gRPC from the same .proto, keeping one source of truth. Browsers can't speak native gRPC without gRPC-Web and a proxy, and federation is a GraphQL composition technique.

</MCQ>

<MCQ q="Which statement about the three API styles is correct?" options={["gRPC can run over HTTP/1.1 if trailers are disabled", "gRPC requires HTTP/2, uses Protobuf, and needs gRPC-Web plus a proxy to be called from browsers", "GraphQL requires Protobuf schemas", "REST requires a typed contract such as OpenAPI"]} answer={1}>

gRPC depends on HTTP/2 features, including trailers that carry grpc-status, and browsers need gRPC-Web. GraphQL uses its own SDL, and OpenAPI is optional for REST.

</MCQ>

</Quiz>

## TL;DR cheat sheet

| | REST | gRPC | GraphQL |
|---|---|---|---|
| Transport | HTTP/1.1 or 2 | HTTP/2 (required) | HTTP (POST) or WS |
| Payload | JSON | Protobuf binary | JSON |
| Typed contract | Optional (OpenAPI) | Required (`.proto`) | Required (SDL) |
| Streaming | Limited (SSE, WS) | First-class, 4 modes | Subscriptions over WS |
| Browser-native | Yes | No (grpc-web needed) | Yes |
| Discoverable | URLs + docs | reflection + proto | introspection |
| HTTP caching | Easy (GET) | No | Hard (POST) |
| Best for | Public APIs | Internal microservices | Client-driven shape |
