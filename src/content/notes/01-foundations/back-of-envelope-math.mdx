## Definition (interview-ready)

**Back-of-envelope estimation** is the practice of using rough orders of magnitude — for throughput (QPS), storage, bandwidth, and latency — to decide whether a system design is plausible before committing to it. You memorize a small set of base numbers (latencies, seconds per day, bytes per item), then multiply and divide to get answers that are right to within a factor of 2–10. The goal is not precision; it is to find which resource (CPU, memory, disk, network) is the bottleneck and how many machines the design needs.

**One-liner:** Back-of-envelope math is turning user counts and payload sizes into rough QPS, storage and bandwidth numbers, using memorized latency figures, so you can check a design is feasible before you build it.

## Why it matters

Every system design interview opens with capacity numbers: "100M DAU, 5 posts per user, 1KB per post." If you can't translate that to QPS, GB/day, and IOPS, you can't choose a database, a sharding strategy, or a cache size. In the real world, the same skill stops you from over-engineering for traffic that won't come (or under-provisioning a launch).

## Core numbers to memorize (Jeff Dean, updated)

```
L1 cache reference                 0.5 ns
Branch mispredict                    5 ns
L2 cache reference                   7 ns
Mutex lock/unlock                   25 ns
Main memory reference              100 ns           (~200× L1)
Compress 1KB with Snappy         3,000 ns  (3 μs)
Send 1KB over 1 Gbps network    10,000 ns  (10 μs)
SSD random read              150,000 ns  (150 μs)
Read 1MB sequentially from RAM  250,000 ns  (250 μs)
Round trip within datacenter    500,000 ns  (500 μs = 0.5 ms)
Read 1MB sequentially from SSD 1,000,000 ns  (1 ms)
HDD seek                       10,000,000 ns  (10 ms)
Read 1MB sequentially from HDD 20,000,000 ns  (20 ms)
Round trip CA → Netherlands   150,000,000 ns  (150 ms)
```

### Useful conversions

- **1 ns** = 10⁻⁹ s. **1 ms** = 10⁻³ s.
- **1 byte** = 8 bits. **1 KB** = 10³ B, **1 MB** = 10⁶ B, **1 GB** = 10⁹ B (decimal — disks/networks use these).
- **1 Gbps** = 125 MB/s.
- **86,400 seconds in a day** — call it ~10⁵.
- **30M seconds in a year** — call it ~3 × 10⁷.

### Throughput conversions

- **DAU → QPS**: `DAU × actions_per_user / 86,400`. 100M DAU × 10 actions = 1B/day ≈ 12K QPS average. Peak = ~3× average.
- **Storage / day**: `events_per_day × bytes_per_event`.
- **Bandwidth**: `QPS × payload_size`.

## How to apply (template)

For any HLD problem:

1. **Users & actions**: DAU, actions per user per day → average QPS, peak QPS.
2. **Read/write ratio**: typically 100:1 for social feeds, 1:1 for chat, 10:1 for e-commerce.
3. **Payload sizes**: tweet 1KB, image 200KB, video clip 5MB.
4. **Storage per day**: writes/day × payload.
5. **Storage per 5 years**: × ~2000 days. (Useful when sizing data lakes.)
6. **Bandwidth**: peak QPS × payload. Inbound and outbound.
7. **Cache size**: hot fraction (often 20%) × dataset.
8. **Connections**: with persistent conns, QPS / RPS-per-conn ≈ active conns.

## Worked example: a Twitter feed

- 300M DAU, each posts 2 tweets/day → 600M tweets/day → ~7K writes/sec average, ~21K peak.
- Each reads 100 tweets/day → 30B reads/day → ~350K reads/sec average, ~1M peak.
- 1KB per tweet → 600 GB writes/day → ~200 TB/year (raw).
- Outbound bandwidth at peak: 1M reads/sec × 1KB = 1 GB/s.

**Immediate conclusions**:
- Reads outnumber writes ~50× (30B vs 600M per day). Cache aggressively.
- 1M QPS reads = sharded read replicas + Redis layer + CDN for media.
- 200 TB/year + replication factor 3 → 600 TB/year actually stored. Tiered storage (hot in MySQL/Cassandra, cold in S3/parquet).
- 1 GB/s outbound → CDN handles media; tweet text fits in low GB/s easily.

## Real-world examples

- **WhatsApp**: famously ran a massive messaging service with a tiny team (~50 engineers for ~900M users in 2015). Per-server connection math drove the design: in 2012 they reported pushing a single Erlang/FreeBSD server past 2M concurrent TCP connections.
- **Instagram**: ~95M photos and videos shared per day (2016 figure). At 200KB avg + RF=3 ≈ 60 TB/day new storage. Hence blob storage + CDN, not a database, for media.
- **Latency budgets (illustrative)**: if a multi-step API (say, a payment flow) has an end-to-end p99 target of ~100 ms and makes several internal hops in sequence, each hop gets a budget of roughly 10 ms. Budgets like this push teams toward co-located services and tight caching.

## Common pitfalls

- **Mixing decimal and binary units**: disk vendors say 1 TB = 10¹² bytes; OS says 1 TiB = 2⁴⁰. Be consistent.
- **Forgetting peak ≠ average**: real traffic is bursty. Apply 2–5× peak factor.
- **Forgetting replication**: storage estimates need × replication factor (typically 3).
- **Ignoring metadata**: indexes can be 20-50% of data size; logs can equal the data they describe.
- **Conflating read latency with write latency**: writes often need fsync, replication ACKs, much slower than reads.
- **Wishful caching**: "we'll cache it" doesn't help if access pattern has no locality.

## Practice questions

<Practice>

<QA q="How much faster is RAM than an SSD random read?" level="easy">

RAM access is ~100 ns and an SSD random read is ~150 μs, so the SSD is ~1,500× slower. For big sequential blocks the gap shrinks: reading 1 MB sequentially takes ~250 μs from RAM vs ~1 ms from SSD (about 4× slower).

</QA>

<QA q="Convert 100M DAU doing 10 actions per day into average and peak QPS." level="easy">

100M × 10 = 1B actions/day. Divide by 86,400 s (≈ 10⁵): ~12K QPS on average. Real traffic is bursty, so apply a 2–5× peak factor; ~3× gives ~35K QPS at peak. Always size for peak, not average.

</QA>

<QA q="How much data does 100M DAU posting 1 tweet per day (1 KB) generate per year?" level="easy">

100M × 1 KB/day = 100 GB/day. × 365 ≈ 36 TB/year. With replication factor 3, ~110 TB/year actually on disk.

</QA>

<QA q="How many MB/s does a 1 Gbps link carry, and why do the units trip people up?" level="easy">

1 Gbps = 10⁹ bits/s ÷ 8 = **125 MB/s** (10 Gbps ≈ 1.25 GB/s). Networks are quoted in bits, storage in bytes, so forgetting the ÷8 is an 8× error. Also keep decimal (1 TB = 10¹² B, what disks and networks use) separate from binary (1 TiB = 2⁴⁰ B, what the OS often shows).

</QA>

<QA q="A service needs to serve 1M QPS with a 2 KB response each. How much bandwidth?" level="medium">

1M × 2 KB = 2 GB/s = 16 Gbps. You need fat NICs (40/100 Gbps) at the edge, spread across many machines, or a CDN to absorb the egress.

</QA>

<QA q="500M users, one timestamp per user updated on every login. How big is the table?" level="medium">

500M × ~30 bytes (8 B user_id + 8 B timestamp + ~14 B row overhead) ≈ 15 GB. With an index, ~30 GB. That fits in RAM on one machine, so this alone needs no sharding.

</QA>

<QA q="Which multipliers do people most often forget when estimating storage?" level="medium">

- **Replication factor** (typically × 3).
- **Indexes and metadata**: indexes can be 20–50% of data size; logs can equal the data they describe.
- **Retention horizon**: 5 years is ~2,000 days, not 365.
- **Peak vs average** for the write rate that feeds the storage.

Missing any one of these is an easy 2–3× underestimate.

</QA>

<QA q="A request fans out to 5 internal services, each with p99 = 20 ms. What is the end-to-end p99?" level="medium">

**Not 20 ms.** With wait-for-all fan-out you wait for the slowest of 5 calls. If they're independent, P(all 5 under 20 ms) = 0.99⁵ ≈ 0.95, so ~5% of requests exceed 20 ms and 20 ms is now roughly your end-to-end **p95**. The end-to-end p99 is each call's ~p99.8, which, depending on the tail shape, can be several times 20 ms. Fan-out amplifies tail latency (Dean & Barroso, "The Tail at Scale").

</QA>

<QA q="You're sizing a cache for 10 TB of warm data with an 80% hit-rate target. What's the budget?" level="hard">

With Zipfian (skewed) access, an 80% hit rate usually needs ~20% of the working set cached: ~2 TB. At ~50 GB usable per Redis node (leaving overhead), that's ~40 nodes. If the access pattern is flatter than assumed, you may need closer to 30% (~3 TB). And if access has no locality at all, caching won't reach 80% at any sane size.

</QA>

<QA q="Design a write-heavy logging system at 1M events/sec, 200 bytes each. Estimate storage and bandwidth for a year." level="scenario">

- Throughput: 1M × 200 B = 200 MB/s = 1.6 Gbps ingress (~3× compression → ~0.5 Gbps on the wire).
- Per day: 200 MB/s × 86,400 ≈ 17 TB raw, ~6 TB compressed.
- Per year: ~6 PB raw, ~2 PB compressed, ~6 PB compressed with RF=3.
- Conclusion: tiered storage, columnar format (Parquet), partition by date + tenant, move to cold storage (e.g. S3 Glacier) after 30 days, query with Trino/Presto.

</QA>

<QA q="A new feature predicts 5M extra DAU. Each 30-minute session makes 50 API calls with 5 KB responses. What infra grows?" level="scenario">

- Concurrent sessions at peak (assuming one session per user per day, 3× avg): 5M × (30 / 1,440) × 3 ≈ 300K active.
- API peak: 5M × 50 / 86,400 × 3 ≈ 8.7K QPS of new load.
- Bandwidth: 8.7K × 5 KB ≈ 45 MB/s ≈ 350 Mbps egress.
- ~300K concurrent connections matter for LBs and connection pools far more than bandwidth does.
- DB reads/writes depend on the feature mix; have a back-pressure plan before launch.

</QA>

<QA q="Your estimate shows 300M DAU, 100:1 reads to writes, ~1M read QPS at peak and 1 GB/s egress. What design decisions follow?" level="scenario">

- Reads dominate by 100×, so **cache aggressively** (a Redis layer in front of sharded read replicas).
- 1M read QPS is far beyond one database, so shard and replicate.
- 1 GB/s egress is fine for text; push media through a **CDN** rather than your servers.
- Storage (~200 TB/year raw, ~600 TB with RF=3) argues for **tiered storage**: hot data in MySQL/Cassandra, cold in S3/Parquet.

The point of the math is these conclusions: it picks the architecture.

</QA>

</Practice>

## Quiz

<Quiz>

<MCQ q="100M DAU each perform 10 actions per day. Roughly what is the average QPS?" options={["~1.2K", "~12K", "~120K", "~1.2M"]} answer={1}>

1B actions/day ÷ 86,400 s ≈ 11.6K, so ~12K QPS. The other options are off by a factor of 10 or more, the classic mistake when you lose track of the 10⁵ seconds in a day.

</MCQ>

<MCQ q="Which ordering from fastest to slowest is correct?" options={["SSD random read, RAM reference, datacenter round trip, HDD seek", "RAM reference, datacenter round trip, SSD random read, HDD seek", "RAM reference, SSD random read, datacenter round trip, HDD seek", "RAM reference, SSD random read, HDD seek, datacenter round trip"]} answer={2}>

RAM ~100 ns, SSD random read ~150 μs, datacenter round trip ~500 μs, HDD seek ~10 ms. An SSD random read is faster than a network round trip in the same datacenter, and an HDD seek is slower than both.

</MCQ>

<MCQ q="A service serves 1M QPS with 2 KB responses. What egress bandwidth is needed?" options={["2 Gbps", "250 Mbps", "160 Gbps", "16 Gbps"]} answer={3}>

1M × 2 KB = 2 GB/s, and × 8 bits per byte = 16 Gbps. 2 Gbps forgets the bits-vs-bytes conversion; the others are off by an order of magnitude.

</MCQ>

<MCQ q="A request fans out to 5 independent services, each with p99 = 20 ms, and waits for all of them. What is true?" options={["Roughly 5% of requests will take longer than 20 ms", "The end-to-end p99 is exactly 20 ms", "The end-to-end p99 is 100 ms because latencies add", "Fan-out improves tail latency because calls run in parallel"]} answer={0}>

P(all 5 under 20 ms) = 0.99⁵ ≈ 0.95, so ~5% exceed it and 20 ms becomes roughly the p95. Parallel calls don't add latencies, but waiting for the slowest one amplifies the tail rather than improving it.

</MCQ>

<MCQ q="You estimated 200 TB/year of raw writes. Which figure is the most realistic disk footprint to plan for?" options={["200 TB, since the raw estimate is what gets stored", "About 600 TB or more, after replication factor 3 plus index overhead", "About 70 TB, since compression always gives 3x", "About 20 TB, since only the hot 10 percent is kept"]} answer={1}>

Storage must be multiplied by the replication factor (typically 3), and indexes and metadata add 20–50% on top. Compression and tiering can help, but you can't assume them by default.

</MCQ>

<MCQ q="Why size infrastructure with a peak factor of 2 to 5x rather than for average QPS?" options={["Averages are always computed incorrectly", "Replication triples the request rate", "Real traffic is bursty, and capacity planned for the average falls over at peak", "Caches only work at peak load"]} answer={2}>

Traffic follows daily cycles and spikes, so a system sized for the average is overloaded for a good part of the day. Replication affects storage, not client QPS, and caches help at any load.

</MCQ>

<MCQ q="An 80% cache hit rate on 10 TB of warm data is the goal. Which assumption makes caching about 2 TB reasonable?" options={["Access is uniformly random across all keys", "The cache uses SSDs instead of RAM", "Every key is read exactly once", "Access is skewed (Zipfian), so a small hot set receives most reads"]} answer={3}>

Under skewed access a ~20% hot set can serve most reads. With uniform access, the hit rate roughly equals the fraction cached, so 2 TB would give about 20%. Keys read only once have no locality to exploit.

</MCQ>

<MCQ q="A design has a 100:1 read-to-write ratio and about 1M read QPS at peak. What is the most direct conclusion?" options={["Put a cache layer and read replicas in front of the primary store", "Switch to a write-optimized LSM database", "Add more write shards to the primary", "Drop replication to save capacity"]} answer={0}>

When reads dominate by 100×, the win is serving reads from caches and replicas. Write optimizations and write shards target the wrong side of the ratio, and dropping replication sacrifices durability without helping read QPS.

</MCQ>

</Quiz>

## TL;DR cheat sheet

- L1 → 0.5 ns. RAM → 100 ns. SSD random → 150 μs. Datacenter RTT → 0.5 ms. Cross-continent RTT → 150 ms.
- 1 Gbps = 125 MB/s. 1 day = 86,400 s ≈ 10⁵.
- Peak ≈ 2–5× average.
- Read-heavy social = ~100:1 R/W. Cache the reads.
- Always multiply storage by replication factor (× 3 typical).
- Fan-out amplifies tail latency. p99 of N calls » p99 of one.
- When in doubt, compute QPS first, then storage/day, then bandwidth.
