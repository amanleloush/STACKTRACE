## Definition (interview-ready)

**Schema evolution** is the discipline of changing data formats (DB schemas, event/message schemas, API contracts) over time without breaking existing producers and consumers. **Backward compatibility** = newer consumers can read older data. **Forward compatibility** = older consumers can read newer data. **Full compatibility** = both.

**One-liner:** Schema evolution is changing data formats and APIs without breaking whoever is still on the old version: make additive changes with defaults, never reuse or retype fields, enforce compatibility with a schema registry, and do destructive database changes as expand, migrate, contract across separate deploys.

## Why it matters

In a system with N services, M deploys per day, and a Kafka topic carrying 6 months of history, every schema change is a potential outage if you don't manage compatibility. Schema evolution discipline is what separates teams that can deploy 100 times a day from those that can deploy weekly.

```mermaid

    A[Old schema] -->|expand| B[Both columns / fields]
    B -->|migrate consumers| C[Switch readers to new]
    C -->|migrate producers| D[Switch writers to new]
    D -->|contract| E[Drop old column / field]
```

## Core concepts

### Why schema changes are hard in distributed systems

- Producers and consumers deploy at different times.
- Stored data (DB, topics, S3) outlives any single deploy.
- Rolling deploys mean both old and new versions run simultaneously.
- A schema-incompatible change breaks the older or the newer side.

### Compatibility types

| Mode | Data written with | Read with | Meaning |
|---|---|---|---|
| Backward | old schema | new schema | new code reads old data |
| Forward | new schema | old schema | old code reads new data |
| Full | either | either | both directions work |

Most systems require **backward** compatibility (new consumers must read old data). Forward compatibility is desirable when older consumers may receive newer data (e.g., rolling deploy where producers ship before consumers).

### Avro, Protobuf, JSON Schema

#### Protobuf (Protocol Buffers)

- Each field has a **field number** (the wire identity).
- Rules: never reuse a field number; don't change a field's type (only a few wire-compatible swaps, such as int32 to int64, are allowed); never add a `required` field (proto2 only; proto3 has no required fields); when deleting a field, mark its number and name `reserved`.
- Result: additive evolution is easy. Breaking change = bump version (new message type).

```protobuf
syntax = "proto3";

message User {
  reserved 4;        // do not reuse the number
  reserved "phone";  // or the name
  int64 id = 1;
  string name = 2;
  string email = 3;
  // 4 was 'phone', removed
  string country = 5;  // added
}
```

#### Avro

- Schema travels with data (or referenced via schema ID).
- **Schema Resolution**: at read time, reader uses its schema and the writer's schema to map fields. Default values in the reader schema let it handle missing fields from older writers.
- Strong support for evolution if you follow rules: give added fields a default (so new readers can read old data), give any field you might later remove a default (so old readers can read new data), and don't change types except Avro's allowed promotions (such as int to long).

#### JSON Schema

- Less rigorous than Avro/Protobuf; depends on convention.
- Tools (Ajv) validate against versioned schemas.
- For events: add optional fields freely, never repurpose names, document.

### Schema registry

A centralized service (Confluent Schema Registry, Apicurio, AWS Glue Schema Registry) that:
- Stores schemas per topic/subject.
- Validates compatibility on register (rejects breaking changes by default).
- Provides schema IDs for serialization — the Confluent wire format is `<magic byte 0><4-byte schema_id><payload>`.

Compatibility modes (Confluent SR):
- BACKWARD (default): new schema can be used to read data written with prev schema.
- FORWARD: old schema can read data written with new schema.
- FULL: both.
- NONE: no compatibility enforcement (don't).

### Database schema migrations

Different from event schema, similar principles:

#### Online schema change

For zero-downtime:
1. **Add new column** (nullable / with default).
2. **Backfill** in batches (don't lock-update millions of rows at once).
3. **Dual-write** if writers exist that don't know the new column.
4. **Switch reads** to use the new column.
5. **Remove the old column** in a later release.

For renames, type changes, anything destructive — always do the **expand-migrate-contract** dance.

#### Expand-migrate-contract

1. **Expand**: add new schema element (column, field, table).
2. **Migrate**: deploy code that writes to both; backfill historical data.
3. **Contract**: remove the old element when all code uses the new.

Each phase is a deploy. Never combine.

#### Tools

- **gh-ost** (GitHub), **pt-online-schema-change** (Percona): online MySQL schema changes.
- **pg_repack** (Postgres): rebuild tables online.
- **Liquibase / Flyway**: migration tooling.
- **Atlas**: declarative schema management.

### API versioning

- **URL versioning**: `/v1/orders`, `/v2/orders`. Explicit, easy to debug.
- **Header versioning**: `Accept: application/vnd.example.v2+json`. Clean URLs.
- **Query parameter**: `/orders?version=2`. Less common.

For gRPC: new service or new package (`mypackage.v2`).

For GraphQL: evolve the schema additively — deprecate fields first and remove them only after usage has dropped to zero (or never). Clients pick the fields they want.

### Strategies for breaking changes

When you genuinely have to break:
- **Dual-publish**: producer writes both old and new schema during transition.
- **Adapter / translation layer**: at the edge, translate between versions.
- **Versioned consumer groups**: old consumers on a deprecated topic, new on the new topic.
- **Sunset timeline**: announce, deprecate, monitor usage, remove.

### Data formats and evolution

| Format | Schema | Evolution support |
|---|---|---|
| JSON | implicit | flexible but no enforcement |
| JSON Schema | explicit | manual evolution |
| Avro | embedded or referenced | strong (default values, aliases) |
| Protobuf | external `.proto` | strong (field numbers) |
| Parquet | embedded | column-add OK; renames hard |
| ORC | embedded | similar |

For analytics: Avro / Parquet with **schema-on-read** is common — old files keep their schema, new files have new schema, query engines (Trino, Spark) handle the merge.

## How it works (adding a field with Protobuf + schema registry)

```
1. Update .proto: add `optional string referrer = 6;` — new field number.
2. Submit to schema registry: SR validates "BACKWARD compatible" (new optional field
   is backward compatible). Approved.
3. Deploy producer: emits events with optional new field. Old consumers ignore the
   unknown field number.
4. Deploy consumer: reads new field (with default if absent).
5. Historical data: pre-update events don't have the field; consumer sees default.
```

## Real-world examples

- **Confluent Schema Registry**: Industry standard for Kafka.
- **LinkedIn's Pegasus**: the schema language behind Rest.li, with its own compatibility checks.
- **Stripe API**: rare breaking changes; versioning via date headers (`Stripe-Version: 2024-04-10`).
- **GitHub REST API**: date-based versions via the `X-GitHub-Api-Version: 2022-11-28` header (replacing the older `Accept: application/vnd.github.v3+json` convention).
- **Google APIs**: gRPC + Protobuf evolution discipline.
- **Shopify GraphQL APIs**: quarterly date-based versions (e.g. `2025-01`); fields are deprecated first and removed only in a later version.

## Common pitfalls

- **Reusing a removed field number** in Protobuf → silent corruption.
- **Changing a field's type** (string → int) → silent corruption.
- **Adding a required field** to an Avro schema without default → breaks old data.
- **Combining expand + contract** in one deploy → breaks whichever version of the code is still running during the rollout.
- **Dropping a database column with `ALTER TABLE DROP`** while old code still writes to it → 500 errors.
- **Migrating data in a giant single `UPDATE`** → long locks, blocking, replica lag.
- **Schema "drift" without registry** → producers and consumers disagree silently.
- **GraphQL: removing a field while clients depend on it** → broken clients. Deprecate, monitor, remove later.
- **JSON evolution by convention** → eventually a field rename slips through.

## Practice questions

<Practice>

<QA q="What's the difference between backward and forward compatibility?" level="easy">

**Backward** = newer consumers can read older data (fields added in the new schema need defaults; deleting fields is fine). **Forward** = older consumers can read newer data (they ignore unknown fields). **Full** = both. The default goal in most systems is backward compatibility.

</QA>

<QA q="Why can you never reuse a field number in Protobuf?" level="easy">

The field number is the wire identity. Old binaries reading new data with a recycled number decode the bytes as the old field's type — silent data corruption. Always mark removed field numbers `reserved` in the `.proto`.

</QA>

<QA q="What are the common ways to version an HTTP API?" level="easy">

- **URL**: `/v1/orders`, `/v2/orders` — explicit and easy to debug.
- **Header**: e.g. `Accept: application/vnd.example.v2+json` — clean URLs. Stripe and GitHub use date-based version headers.
- **Query parameter**: `/orders?version=2` — less common.

For gRPC, use a new service or package (`mypackage.v2`). GraphQL is additive: deprecate fields rather than removing them, since clients pick the fields they need.

</QA>

<QA q="What does a schema registry do?" level="medium">

A central service (Confluent Schema Registry, Apicurio, AWS Glue Schema Registry) that stores schemas per subject, **validates compatibility on register** and rejects breaking changes, and hands out schema IDs used in serialization — the Confluent wire format is a magic byte 0, a 4-byte schema ID, then the payload. Confluent's modes are BACKWARD (the default), FORWARD, FULL, their transitive variants such as `BACKWARD_TRANSITIVE` (checked against all earlier versions, not just the latest), and NONE.

</QA>

<QA q="How would you safely add a NOT NULL column to a 50M-row table?" level="medium">

- **Expand**: `ALTER TABLE t ADD COLUMN c ... DEFAULT ...`. Postgres 11+ does this without rewriting the table when the default is non-volatile (a constant, not e.g. `random()`).
- **Backfill** in chunks (`UPDATE ... WHERE id BETWEEN X AND Y`), committing between small batches.
- **Migrate**: deploy code that writes the column.
- **Contract** (optional): enforce NOT NULL once the backfill is done; drop the default if it shouldn't be permanent. In Postgres, `SET NOT NULL` scans the whole table under an exclusive lock; to avoid that, first add `CHECK (c IS NOT NULL) NOT VALID`, then `VALIDATE CONSTRAINT` (no long lock), and Postgres 12+ can then set NOT NULL without the scan.
- For MySQL, use an online schema-change tool (gh-ost, pt-online-schema-change) if blocking is a concern.

</QA>

<QA q="A team adds a required field to a Kafka event schema. What breaks?" level="medium">

Old data lacks the field, so newer consumers with strict validation reject it or crash. Older producers don't emit it, so newer consumers get incomplete data. With BACKWARD compatibility set, the schema registry should reject the change at register time. Fix: make the field optional, or give it a default.

</QA>

<QA q="Walk through expand-migrate-contract." level="medium">

- **Expand**: add the new schema element (column, field). Old code doesn't use it.
- **Migrate**: deploy code that reads and writes the new element; backfill historical data; run side by side.
- **Contract**: remove the old element once all code has migrated and the old data is no longer needed.

Each phase is a separate deploy — never combine them. That way no running version of any service breaks.

</QA>

<QA q="Why is changing a field's type (e.g., string to int) treated as a breaking change?" level="medium">

Data already written with the old type still exists in topics, tables and files, and old and new code run side by side during rolling deploys. Readers decode bytes using the wrong type, which fails loudly at best and silently corrupts data at worst. Instead, add a new field with the new type, dual-write, migrate readers, and retire the old field via expand-migrate-contract.

</QA>

<QA q="Compare schema evolution in Avro, Protobuf, and JSON." level="hard">

- **Avro**: schema resolution on read — the reader maps the writer's schema to its own; default values and aliases support evolution well. Readers need the writer schema, usually from a registry.
- **Protobuf**: field-number wire format with strict rules; widely tooled (gRPC); good for service contracts.
- **JSON**: implicit schema; flexible but error-prone; needs JSON Schema plus tooling to enforce anything.

Choose Protobuf for service contracts (gRPC), Avro for streaming and analytics (Kafka + Schema Registry), JSON for browser APIs and human debugging.

</QA>

<QA q="How do you handle a change that genuinely has to break compatibility?" level="hard">

- **Dual-publish**: the producer writes both old and new formats during the transition.
- **Adapter / translation layer** at the edge to translate between versions.
- **Versioned topics or consumer groups**: old consumers stay on the deprecated topic, new ones move to a `.v2` topic.
- **Sunset timeline**: announce, deprecate, monitor usage, and remove only when usage reaches zero.

</QA>

<QA q="Design schema evolution for a multi-team Kafka topic." level="scenario">

- Producers and consumers use a **schema registry**; the subject uses **BACKWARD** compatibility.
- Change contract:
  - Adding optional fields: free.
  - Removing fields: deprecate, monitor consumer usage, remove only at zero usage.
  - Renaming: deprecate the old name, add the new one, dual-publish during the transition.
  - Breaking: a new topic or `.v2` suffix.
- Track changes through reviewed 'topic evolution' PRs.
- Alert when a consumer hits unknown-schema-ID errors.

</QA>

<QA q="You discover the production schema diverged from the `schemas/` repo. How did it happen, and how do you prevent it?" level="scenario">

Likely causes: **no CI gate** validating schema PRs against the running registry; **direct prod changes** through the registry API; **tool sprawl** (some services use a different registry or none); or an engineer **ad-hoc registering** a local schema while testing with a console producer.

Fix: schema-only PRs, CI that checks against the registry, locked-down direct registry access, and one source of truth (the `schemas/` repo with codeowners).

</QA>

<QA q="A deploy drops a column with ALTER TABLE DROP and the API starts returning 500s. What went wrong, and what's the safe procedure?" level="scenario">

Old code — still running during the rolling deploy, or other services sharing the table — was still reading or writing the column. Contract happened before migrate was complete. Safe procedure: first deploy code that no longer reads or writes the column and confirm every version and service is off it (logs, query stats); only then drop it in a **later** release. If the table is large, use an online schema-change tool to avoid long locks.

</QA>

<QA q="You need to rename a column used by three services without downtime. Plan it." level="scenario">

1. **Expand**: add the new column.
2. **Dual-write**: deploy writers that write both columns.
3. **Backfill** old rows into the new column in small batches (no single giant `UPDATE` — long locks and replica lag).
4. **Switch reads** in each service to the new column, one deploy at a time.
5. **Stop writing** the old column once no reader uses it.
6. **Contract**: drop the old column in a later release.

</QA>

</Practice>

## Quiz

<Quiz>

<MCQ q="Consumers are upgraded first and must read events written with the previous schema. Which compatibility mode does that require?" options={["Forward", "Backward", "None", "Transitive forward only"]} answer={1}>

Backward compatibility means new-schema readers can read old-schema data, which is exactly the case where consumers upgrade first. Forward is the reverse (old readers, new data); None enforces nothing; forward-only modes don't cover it.

</MCQ>

<MCQ q="A Protobuf field number 4 (phone) was removed. A developer wants to use 4 for a new int64 field. What is the risk?" options={["The compiler always rejects it, so there's no risk", "Only a performance penalty", "Old binaries and old stored data decode the bytes as the wrong field, silently corrupting data", "None, as long as the field name is different"]} answer={2}>

The field number is the wire identity, so old data and old code will interpret field 4 bytes with the old meaning. The compiler only blocks it if 4 is marked reserved, which is the point of reserving it; names don't appear on the wire.

</MCQ>

<MCQ q="Which change is safe under BACKWARD compatibility in Avro?" options={["Adding a field with a default value", "Adding a required field with no default", "Changing an int field to a string", "Renaming a field without an alias or default"]} answer={0}>

A new field with a default lets new readers fill in the value when reading old data. A required field without a default, an int-to-string type change, or a rename with no alias all leave the new reader unable to resolve old data.

</MCQ>

<MCQ q="Why should expand, migrate and contract be separate deploys?" options={["Databases only allow one DDL per day", "Separate deploys make migrations faster", "Schema registries require it", "During rolling deploys old and new code run together, so each step must work with both versions"]} answer={3}>

Old and new versions coexist during deploys, so each step must be compatible with both. Combining contract with expand breaks whichever version is still running. There is no DDL-per-day limit and it isn't a registry rule or a speed trick.

</MCQ>

<MCQ q="In the Confluent wire format, what precedes the serialized payload?" options={["The full schema JSON", "A magic byte 0 and a 4-byte schema ID", "The topic name and partition", "A CRC32 checksum only"]} answer={1}>

The Confluent format is a magic byte followed by a 4-byte schema ID, which the consumer uses to fetch the writer schema from the registry. Embedding the full schema would bloat each message; topic and partition aren't in the payload; the checksum isn't the framing.

</MCQ>

<MCQ q="On Postgres 11 or later, why is ADD COLUMN ... DEFAULT 0 cheap even on a huge table?" options={["Existing rows are left without the column and return NULL", "It runs in the background over several days", "A non-volatile default is stored once in the catalog instead of rewriting the table", "Postgres converts the table to columnar storage"]} answer={2}>

Postgres 11+ records a non-volatile default in the catalog and returns it for existing rows, so no table rewrite is needed. A volatile default like random() still forces a rewrite. Existing rows return the default, not NULL; it isn't a background job and doesn't change the storage format.

</MCQ>

<MCQ q="A team must backfill a new column on 50M rows. Which approach is safest?" options={["Small batched UPDATEs with commits between batches", "One UPDATE over the whole table in a single transaction", "Drop and recreate the table", "Rename the old table and copy rows during peak hours"]} answer={0}>

Small batches keep locks short and limit replica lag. A single huge UPDATE holds locks for a long time and spikes lag; dropping or renaming the live table causes downtime.

</MCQ>

<MCQ q="Which is the best tool choice for internal service-to-service contracts per the note?" options={["Plain JSON without a schema", "Parquet", "CSV with a header row", "Protobuf with gRPC"]} answer={3}>

Protobuf has strict, field-number-based evolution rules and first-class gRPC tooling, which suits service contracts. Plain JSON has no enforcement, Parquet is an analytics file format, and CSV has no real evolution story.

</MCQ>

<MCQ q="How should a GraphQL API retire a field that clients may still use?" options={["Remove it immediately; clients choose their fields anyway", "Deprecate it, monitor usage, and remove it later", "Change its type to null", "Rename it in place"]} answer={1}>

GraphQL evolves additively: mark the field deprecated, watch usage, and remove it only when clients have moved. Removing, retyping or renaming in place breaks clients that still query it.

</MCQ>

</Quiz>

## TL;DR cheat sheet

- **Backward** = new code reads old data. **Forward** = old code reads new data. **Full** = both.
- Adding optional/defaulted fields = safe.
- Removing fields = deprecate first; only contract when usage = 0.
- Never reuse Protobuf field numbers; mark them `reserved`.
- Type changes = breaking; never silent.
- Database migrations: **expand → migrate → contract** across deploys.
- Use a **schema registry** for streaming/Kafka. Enforce compatibility in CI.
- API versions: URL or header; GraphQL is additive (deprecate, don't remove).
- Online schema change tools (gh-ost, pt-osc) for big tables.
