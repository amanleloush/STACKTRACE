## Definition (interview-ready)

**CAP theorem**: in the presence of a network **P**artition, a distributed system must choose between **C**onsistency (every read sees the latest write) and **A**vailability (every request gets a response). **PACELC** extends CAP: *if Partition* (PC vs PA), *else* (LC vs LA — Latency vs Consistency). **Consistency models** are a hierarchy ranging from **linearizable** (real-time order) → **sequential** → **causal** → **eventual**, each trading strictness for performance and availability.

## Why it matters

Almost every database brochure overpromises. CAP/PACELC + the consistency hierarchy give you the vocabulary to evaluate claims and to reason about what your system actually guarantees — which matters when correctness bugs appear under failure or contention.

## Core concepts

### CAP theorem (Brewer 2000, proven 2002)

In a distributed system, during a network partition you can guarantee at most two of:
- **Consistency**: all reads see the most recent write (linearizability, technically).
- **Availability**: every request completes (non-error response).
- **Partition tolerance**: system keeps working despite some messages being dropped.

**P is not optional** in any real distributed system — networks fail. So in practice CAP says: **during a partition, choose C or A.**

- **CP**: refuse some requests rather than return stale data (Mongo majority, Zookeeper, etcd, HBase).
- **AP**: return possibly-stale data rather than refuse (Cassandra default, DynamoDB, Riak).

### PACELC (Abadi 2010)

CAP only addresses partitions, which are rare. PACELC says:
- **If Partition: choose C or A** (same as CAP).
- **Else (normal operation): choose L (latency) or C (consistency).**

Every system always trades L vs C even when healthy. Examples:
- **PC/EC** (Spanner): strong consistency always, at the cost of latency.
- **PA/EL** (Cassandra default): availability and low latency, eventual consistency.
- **PC/EL** (Yahoo PNUTS, per Abadi): gives up availability on partition but favors latency otherwise.

### Consistency hierarchy

From strongest (most expensive) to weakest:

```
Strict serializability  ⊃ Linearizability  ⊃ Sequential  ⊃ Causal  ⊃ Eventual
       (Spanner)            (etcd)            (txn order)    (COPS)     (Cassandra default)
```

#### Linearizability

There exists a single global order of operations consistent with real-time order. If op A finishes before op B starts (wall-clock), B sees A's effect. **Strong reads** in Postgres, **Spanner reads**, etcd. (ZooKeeper writes are linearizable, but its reads are not unless preceded by `sync`.)

#### Sequential consistency

All operations appear in some consistent order to all nodes, but **not necessarily real-time order**. Each node's operations appear in its own program order. Weaker than linearizable; rarely used in DBs but common in shared-memory multiprocessors.

#### Causal consistency

Operations causally related (B reads value written by A → A causally precedes B) are observed in causal order by all nodes. Concurrent operations (no causal relation) can be observed in different orders. Sweet spot for social apps — comments-after-posts, replies-after-messages, etc. Implemented via vector clocks or hybrid logical clocks.

#### Eventual consistency

Given no new writes, all replicas eventually converge. No order guarantees in between. Cassandra default, DNS, Amazon S3 (historically).

#### Read-your-writes / monotonic reads (session guarantees)

Weaker than causal but practical:
- **Read-your-writes**: after you write, your reads see at least your write.
- **Monotonic reads**: reads are non-decreasing across time (you never see an older version after seeing a newer one).
- **Monotonic writes**: your writes are applied in the order you submitted them.
- **Writes-follow-reads**: write that follows a read of value v sees v's effect.

These are **session guarantees** — usually implemented via sticky sessions or tracking the user's latest version.

### Strong vs strict serializability vs linearizable

- **Linearizability**: real-time order for *single object* operations.
- **Serializable**: transactions appear as if run serially, but no real-time guarantee.
- **Strict serializability**: serializable + real-time order. The gold standard. What Spanner provides.

### Tradeoff in practice

| System | CAP | PACELC | Why |
|---|---|---|---|
| Spanner | CP | PC/EC | Geo-distributed strong consistency via TrueTime |
| Postgres (single primary) | CP | PC/EC | Primary blocks during partition |
| Postgres replicas | CP+AP mix | PC/EL on replicas | Reads can be stale |
| Cassandra (QUORUM) | CP-ish | PC/EC | Strong via R+W>RF, but availability degraded |
| Cassandra (ONE) | AP | PA/EL | Availability + low latency, eventual |
| DynamoDB (strong read) | CP | PC/EC | Same trade |
| DynamoDB (eventual read) | AP | PA/EL | Fast, possibly stale |
| Redis (no cluster) | CP | PC/EL | Single primary, fast |
| MongoDB (majority) | CP | PC/EC | Quorum writes |
| Kafka | CP | PC/EC | min.insync.replicas writes |

## How it works (a CAP example)

```
3 nodes (A, B, C), one record x=0. Network splits A from {B, C}.

CP system:
  Client writes x=1 to B (majority); B and C update; A doesn't see it.
  Read on A → returns error or blocks (won't return stale 0).
  System sacrifices availability on the A side.

AP system:
  Client writes x=1 to B; B updates locally; replicates async.
  Client on A reads x → returns 0 (stale).
  When partition heals, A converges via repair/anti-entropy.
  System remained available; consistency violated until repair.
```

## Real-world examples

- **Spanner**: CP / PC-EC. Uses atomic clocks + TrueTime API to bound clock skew, achieving global strong consistency.
- **Cassandra**: AP by default; tunable to CP via QUORUM.
- **MongoDB**: write concern majority + read concern majority → strong consistency.
- **DNS**: classic AP. Eventually consistent. Stale records can persist for TTL.
- **S3**: was eventually consistent for years (overwrites, deletes and LISTs could return stale results); became strongly read-after-write consistent in December 2020 — major engineering effort.

## Common pitfalls

- **"We're CP, we're consistent"**: doesn't say anything about latency during normal operation. Use PACELC.
- **Mistaking serializable for linearizable**: serializable transactions can return a snapshot from the past. Linearizable requires real-time order.
- **Assuming "strong consistency" means atomic transactions**: linearizability is per-object; cross-object atomicity requires explicit transactions.
- **Reading from a replica and assuming read-your-writes**: replicas lag. Need sticky session or read-from-primary after write.
- **CRDT lazy-merging surprises**: counters and sets behave well; ordering-dependent operations don't merge cleanly.
- **Believing CAP is one-time choice**: it's per-operation (Cassandra: read at ONE = AP, read at ALL = CP).

## Practice questions

<Practice>

<QA q="State the CAP theorem." level="easy">

In a distributed system, when a network partition occurs, you can guarantee at most two of Consistency, Availability, and Partition tolerance. Since partitions happen in real networks, you must choose between **C and A during a partition**.

</QA>

<QA q="Why do people say P is not optional in CAP?" level="easy">

Any system spread over a network will eventually see dropped or delayed messages — you can't opt out of partitions. So a 'CA' distributed system isn't a real option; the actual decision is what to do **when** a partition happens: refuse some requests (CP) or answer with possibly-stale data (AP).

</QA>

<QA q="Give an example of an AP database and a CP database." level="easy">

**AP**: Cassandra (default), DynamoDB (eventually consistent reads), Riak. **CP**: Spanner, etcd, ZooKeeper, Postgres with synchronous replication, MongoDB with majority write concern.

</QA>

<QA q="What does PACELC add to CAP?" level="medium">

PACELC adds the everyday tradeoff between **latency and consistency even without partitions**. CAP only covers partition-time behavior; PACELC also describes the 'else' case. Partitions are rare, so the everyday L vs C choice matters more. Example: Spanner is PC/EC; Cassandra by default is PA/EL.

</QA>

<QA q="Explain causal consistency and where it helps." level="medium">

Causally related operations (B read a value A wrote, so A precedes B) are seen in causal order by all observers; concurrent, unrelated operations can be seen in any order. Useful for social apps: a reply must appear after the original message, a comment after its post. Cheaper than linearizable, more useful than eventual. Implemented with vector clocks or hybrid logical clocks.

</QA>

<QA q="How does sequential consistency differ from linearizability?" level="medium">

Both require one order of operations that every node agrees on, with each node's operations in its own program order. **Linearizability** additionally requires that order to respect **real time**: if A finishes before B starts, B sees A. Sequential consistency allows a globally agreed order that lags real time. It's common in shared-memory multiprocessors, rarely in databases.

</QA>

<QA q="What are session guarantees, and how are they usually implemented?" level="medium">

Per-client guarantees weaker than causal consistency but practical:
- **Read-your-writes**: your reads see at least your own writes.
- **Monotonic reads**: you never see an older version after a newer one.
- **Monotonic writes**: your writes apply in the order you sent them.
- **Writes-follow-reads**: a write made after reading v is ordered after v.

Usually implemented with sticky sessions or by tracking the user's latest version and reading from a replica that has it.

</QA>

<QA q="Difference between linearizable and serializable." level="medium">

**Linearizable** = real-time order for **single-object** operations. **Serializable** = transactions appear to run in some serial order, with no real-time guarantee — a serializable read can return a snapshot from the past. **Strict serializable** = serializable plus real-time order; Spanner provides it.

</QA>

<QA q="Is the CAP choice made once per database? Explain with Cassandra." level="hard">

No — it's often **per operation**. Cassandra's consistency level is set per request: reads and writes at `ONE` favor availability and latency (AP, PA/EL), while `QUORUM` with `R + W` greater than RF gives strong single-key reads at the cost of availability when too many replicas are unreachable. DynamoDB likewise offers eventual or strongly consistent reads per request.

</QA>

<QA q="How does Google Spanner provide global strong consistency despite WAN delays?" level="hard">

Spanner uses **TrueTime**, an API that returns time as an interval `[earliest, latest]` bounded by GPS and atomic-clock uncertainty (ε typically 1–7 ms, about 4 ms average per the 2012 paper). Commits **wait out** the uncertainty interval before returning, guaranteeing any later transaction gets a strictly greater timestamp. Combined with Paxos replication, this yields external consistency (strict serializability).

</QA>

<QA q="A team claims 'we use Cassandra with QUORUM, so we're consistent.' Critique." level="scenario">

QUORUM with `R + W` greater than RF gives **strong consistency for single-key reads** (within the scope of the quorum). It does **not** give:
- Cross-row atomicity (different keys can be inconsistent).
- Read-your-writes across DCs (`LOCAL_QUORUM` doesn't cross DCs).
- Linearizability under all conditions — that needs Cassandra's LWT (Paxos).
- Protection from clock-skew issues in last-write-wins.

</QA>

<QA q="Design a feed system that needs read-your-writes with a multi-replica DB." level="scenario">

- After a write, route that user's reads to the **primary** for a short window.
- Track a **user version**: the client carries it, and reads wait or retry until the replica has caught up to it.
- **Sticky sessions** to a replica that already has the write.
- A primary-only path for the user's own data; eventually consistent replicas for everything else.

Real systems combine these: write to the primary, write-through cache, then user-affinitized reads.

</QA>

<QA q="During a partition, a 3-node cluster splits into A and B, C. A client on A's side reads key x. How do CP and AP systems respond?" level="scenario">

**CP**: A can't reach a majority, so it returns an error or blocks rather than risk a stale value; writes go through on the B, C majority side. **AP**: A answers with its local, possibly stale value and may accept writes; after the partition heals, replicas converge via repair/anti-entropy, resolving conflicts (e.g., last-write-wins).

</QA>

</Practice>

## Quiz

<Quiz>

<MCQ q="According to CAP, what must a distributed system choose between during a network partition?" options={["Latency and throughput", "Consistency and availability", "Durability and consistency", "Partition tolerance and availability"]} answer={1}>

Partitions can't be avoided in real networks, so P is a given and the choice is C or A while partitioned. Latency only enters with PACELC.

</MCQ>

<MCQ q="What does the EL in a PA/EL system describe?" options={["With no partition, it favors low latency over consistency", "During a partition it favors latency", "It is always linearizable", "It elects a leader on every partition"]} answer={0}>

The E (else) branch describes normal operation: L means it chooses latency over consistency. Cassandra at default settings is the classic PA/EL system.

</MCQ>

<MCQ q="Which system is PC/EC in PACELC terms?" options={["Cassandra at consistency level ONE", "DynamoDB eventually consistent reads", "DNS", "Google Spanner"]} answer={3}>

Spanner keeps strong consistency both during partitions and in normal operation, paying latency for it. The others favor availability and latency.

</MCQ>

<MCQ q="Op A completes before op B starts. Which model guarantees that B observes A's effect?" options={["Eventual consistency", "Causal consistency", "Linearizability", "Sequential consistency"]} answer={2}>

Only linearizability requires the order to respect real time. Sequential consistency needs one agreed order but not a real-time one; causal only orders causally related ops.

</MCQ>

<MCQ q="Why can a serializable database return a result that looks stale to a client?" options={["Serializable allows dirty reads", "Serializable guarantees a serial order but not one that matches real time", "Serializable only applies to writes", "Serializable disables MVCC"]} answer={1}>

Serializable only requires that transactions appear in some serial order, which may place a read before a write that finished earlier in wall-clock time. Strict serializability adds the real-time requirement.

</MCQ>

<MCQ q="A user reads a newer version from one replica, then an older version from another. Which guarantee is violated?" options={["Monotonic writes", "Writes-follow-reads", "Strict serializability only", "Monotonic reads"]} answer={3}>

Monotonic reads promises you never see an older version after a newer one. Sticky sessions to one replica fix this.

</MCQ>

<MCQ q="How does Spanner use TrueTime to guarantee external consistency?" options={["Commits wait out the clock-uncertainty interval before returning", "It synchronizes all clocks to exactly zero skew", "It uses vector clocks instead of physical time", "It routes all writes through one global leader"]} answer={0}>

TrueTime returns a bounded interval; commit-wait ensures the commit timestamp is in the past everywhere before acknowledging. Clocks still have skew, which is why it waits.

</MCQ>

<MCQ q="Cassandra with QUORUM reads and writes and R + W greater than RF guarantees what?" options={["Atomic multi-row transactions", "Read-your-writes across data centers with LOCAL_QUORUM", "Strong consistency for single-key reads", "Immunity from last-write-wins clock skew"]} answer={2}>

Overlapping quorums mean a read sees the latest acked write for that key. Cross-row atomicity, cross-DC guarantees with LOCAL_QUORUM, and clock-skew safety are not provided.

</MCQ>

<MCQ q="Which consistency model best fits ensuring replies always appear after the message they reply to, at low cost?" options={["Strict serializability", "Causal consistency", "Eventual consistency", "Linearizability"]} answer={1}>

Causal consistency orders causally related events (message then reply) without the cost of global real-time ordering. Eventual gives no ordering; the stronger models work but cost more.

</MCQ>

</Quiz>

## TL;DR cheat sheet

- **CAP**: under partition, pick C or A. P is not optional.
- **PACELC**: during partition (P) → C vs A. Else (E) → L vs C.
- Consistency hierarchy: linearizable > sequential > causal > eventual.
- Per-session: read-your-writes, monotonic reads, monotonic writes, writes-follow-reads.
- Linearizable = per-object real-time order. Serializable = transactions appear serial. Strict serializable = both.
- Spanner uses TrueTime for global strict serializability.
- Cassandra QUORUM gives single-key strong consistency, not cross-row atomicity.
- "Strong consistency" is per-object unless you're explicitly in a transaction.
