## Definition (interview-ready)

In a distributed system, **wall-clock time can't be trusted** because clocks drift and aren't perfectly synced. **Logical clocks** capture causal ordering instead of real time:
- **Lamport timestamps**: a single counter per process that orders events causally but **can't distinguish concurrent vs ordered**.
- **Vector clocks**: one counter per process; comparing vectors tells you `<`, `>`, or "concurrent."
- **Hybrid Logical Clocks (HLC)**: combine wall-clock time + logical counter for near-physical ordering with causal guarantees.

**One-liner:** Logical clocks order events by causality instead of unreliable wall time: Lamport timestamps give an order consistent with happens-before, vector clocks can also detect concurrent events, and HLCs keep that causal order while staying close to physical time.

## Why it matters

Wall-clock ordering breaks: replicas with skewed clocks make wrong decisions ("which write won?"). Distributed systems use logical or hybrid clocks for consistency, replication conflict resolution, version vectors, and tracing. Understanding the model determines correctness, not just performance.

## Core concepts

### The clock problem

- **NTP** keeps clocks within ~10s of milliseconds on a good network — but skew is real.
- **Leap seconds** add discontinuities.
- **VM clock drift**: virtual machines can lag or jump.
- **Clock skew between data centers**: easily 100ms+.

Last-write-wins (LWW) using wall-clock time can incorrectly drop a later write whose clock is behind. Cassandra resolves conflicts exactly this way (per-cell LWW on timestamps), so it relies on tightly synced clocks.

### Happens-before relation (Lamport, 1978)

`a → b` (a happens-before b) if:
1. `a` and `b` are in the same process and `a` precedes `b`, OR
2. `a` is a send and `b` is the matching receive, OR
3. Transitivity: `a → c → b`.

Two events are **concurrent** if neither happens-before the other.

### Lamport timestamps

Each process keeps a counter `C`.
- On any event: `C = C + 1`.
- On send: include `C` in the message.
- On receive (with `T`): `C = max(C, T) + 1`.

Guarantee: if `a → b`, then `C(a) < C(b)`.

**But not the reverse**: `C(a) < C(b)` doesn't imply `a → b`. They might be concurrent.

For total ordering, break ties by process ID. Useful for systems that need *some* deterministic order, like Lamport's own distributed mutual-exclusion algorithm or totally ordered broadcast.

### Vector clocks

Each process maintains a vector `V` of length N (one entry per process).
- On any event in process i: `V[i] += 1`.
- On send: include the entire vector.
- On receive (with `W`): `V[j] = max(V[j], W[j])` for all j, then `V[i] += 1`.

Comparing vectors:
- `V1 < V2` iff every `V1[i] ≤ V2[i]` AND at least one `V1[i] < V2[i]` → `V1` happens-before `V2`.
- `V1 = V2` → same event (in theory, unlikely).
- Neither dominates → **concurrent**.

Unlike Lamport timestamps, vector clocks can detect concurrency (and a vector with one entry per process is the minimum size that can do it in general).

### Version vectors (vector clocks for objects)

Same idea but per-object. Used by:
- **Dynamo / Riak**: each object has a version vector; on read with multiple concurrent versions, return them all and let the application reconcile (LWW, app-specific merge, CRDT).
- **DVCS like Git**: not exactly version vectors but similar — partial-order revision history.

### Cost of vector clocks

A vector grows with the number of writer processes. With pruning (drop stale entries when a process is decommissioned), it stays manageable. But unbounded distinct writers = unbounded vector size — a real concern in DBs with many clients writing directly (Cassandra opted not to use full vector clocks for this reason).

### Hybrid Logical Clocks (HLC)

Goal: a timestamp that's close to physical time (so wall-clock readers make sense) but also preserves causal ordering.

```
HLC = (physical_part, logical_part)
On event:
   physical = max(local_physical_clock, last_HLC.physical)
   if physical == last_HLC.physical:
     logical = last_HLC.logical + 1
   else:
     logical = 0
   HLC = (physical, logical)

On receive with HLC_msg:
   physical = max(local_clock, last_HLC.physical, HLC_msg.physical)
   if physical == last_HLC.physical == HLC_msg.physical:
     logical = max(last.logical, HLC_msg.logical) + 1
   elif physical == last_HLC.physical:
     logical = last.logical + 1
   elif physical == HLC_msg.physical:
     logical = HLC_msg.logical + 1
   else:
     logical = 0
   ...
```

Properties:
- Monotonically increasing.
- Close to wall-clock (so it sorts roughly as humans expect).
- Captures happens-before — like Lamport, but with physical anchoring.

Used by: CockroachDB, YugabyteDB, MongoDB (since 3.6 for replica set ordering).

### TrueTime (Spanner)

Google's atomic-clock-backed API: returns time as `[earliest, latest]` interval. Commits wait out the interval to guarantee external consistency (strict serializability). Hardware investment (atomic clocks + GPS in every DC). Practically, HLC achieves much of what TrueTime does without special hardware, at the cost of needing ordinary clock sync (NTP) and weaker guarantees: for example, CockroachDB uses HLC and guarantees serializability, but not strict serializability for every pair of transactions.

### Practical applications

- **Conflict resolution in eventually-consistent stores**: use version vectors to detect conflicts; resolve via app logic, LWW, or CRDTs.
- **CDC ordering across replicas**: HLC for partial orderings.
- **Distributed tracing**: logical/HLC timestamps are one way to order spans across skewed clocks (mainstream tracers rely on the span parent-child tree instead).
- **Snapshot reads in distributed DBs**: HLC timestamps define snapshots.
- **Snapshots in stream processing**: checkpoint barriers tagged with checkpoint IDs (Flink).

## How it works (Lamport on three nodes)

```
P1: C=1 send to P2 with C=1
P2 receives (T=1): C=max(0,1)+1=2; C=3 send to P3 with C=3
P3 receives (T=3): C=max(0,3)+1=4
P1 does another local event: C=2 (independent of P2/P3)

Order:
  Events: (P1,1), (P1,2), (P2,2), (P2,3), (P3,4)
  (P1,1) → (P2,2)  (causal: send/receive)
  (P1,2) and (P2,2): concurrent — equal timestamps tell you nothing
                     about causality; ties are broken by process ID
                     only to get a total order.
```

## Real-world examples

- **Riak / Dynamo**: vector clocks per object → multiple "siblings" on conflict.
- **CockroachDB**: HLC for transaction ordering and snapshot reads.
- **MongoDB**: HLC (since 3.6) for oplog ordering and causal consistency.
- **Cassandra**: uses wall-clock timestamps (LWW), with all the caveats. Knowing this is critical when writing to Cassandra.
- **Google Spanner**: TrueTime for global strict serializability.
- **Distributed tracing (Jaeger, Zipkin)**: spans carry wall-clock timestamps; ordering comes from the parent-child span tree, and UIs apply clock-skew adjustment — a real-world example of why raw timestamps can't be trusted.

## Common pitfalls

- **LWW with wall-clock time**: clock skew can drop later writes. If you must LWW, use HLC or strict clock sync.
- **Vector clocks for many writers**: vector grows unbounded.
- **Believing NTP is accurate enough for ordering**: it isn't, at small intervals (sub-100ms).
- **Forgetting concurrency**: Lamport hides it. If you need to detect conflicts, you need vector clocks.
- **Hybrid clocks without bounded skew**: HLC assumes clocks within some skew bound; far-apart clocks degrade its physical fidelity.

## Practice questions

<Practice>

<QA q="Why can't we trust wall-clock time in distributed systems?" level="easy">

Clocks drift, NTP sync lags, VM clocks can jump, leap seconds add discontinuities, and clocks across regions easily differ by 100 ms or more. Using wall-clock time for ordering or last-write-wins can silently drop the write that actually happened later.

</QA>

<QA q="Define the happens-before relation." level="easy">

`a → b` if (1) `a` and `b` are in the same process and `a` comes first, (2) `a` is a send and `b` is the matching receive, or (3) by transitivity, `a → c` and `c → b`. Two events are **concurrent** if neither happens-before the other.

</QA>

<QA q="What's the difference between Lamport timestamps and vector clocks?" level="easy">

**Lamport**: a single counter per process — orders events consistently with causality, but can't tell whether two events are concurrent or causally related. **Vector clocks**: one counter per process, carried as a vector — can detect concurrency. Lamport is cheap but coarser; vector clocks are richer but grow with the number of processes.

</QA>

<QA q="What are the Lamport clock update rules, and what does the guarantee actually promise?" level="medium">

Each process keeps a counter `C`: increment it on every event, attach it to every message sent, and on receiving timestamp `T` set `C = max(C, T) + 1`. Guarantee: if `a → b` then `C(a)` is less than `C(b)`. **Not** the reverse — a smaller timestamp doesn't mean happened-before; the events may be concurrent. Break ties by process ID to get a total order.

</QA>

<QA q="How do you compare two vector clocks?" level="medium">

`V1` happens-before `V2` if every entry of `V1` is less than or equal to the matching entry of `V2` **and** at least one is strictly less. If `V2` dominates `V1` the other way round, the order flips. If **neither dominates** — each has some entry larger than the other's — the events are **concurrent**. Vector clocks are the structure that can detect this.

</QA>

<QA q="How do vector clocks help in eventually consistent systems?" level="medium">

When two replicas return different versions, comparing their version vectors tells you whether one supersedes the other or they're truly concurrent (a conflict). Conflicts are surfaced to the application (Dynamo/Riak 'siblings') or merged via app logic or a CRDT. Wall-clock LWW can't reliably tell these cases apart.

</QA>

<QA q="What is a Hybrid Logical Clock and why use it?" level="medium">

An HLC timestamp is a `(physical, logical)` pair: the physical part tracks the max wall-clock time seen, and the logical counter increments when physical times tie, preserving causal order. It's monotonic, close to wall-clock (so it sorts roughly as humans expect), and captures happens-before. Used by CockroachDB, YugabyteDB, and MongoDB (since 3.6).

</QA>

<QA q="Why does Cassandra still use wall-clock timestamps despite the LWW risk?" level="medium">

Vector clocks were judged too costly — their size grows with the number of writers (Cassandra clients write directly from many places), and they force a read before write plus application-side merging of siblings. The team chose simpler LWW semantics applied per column (cell), which keeps the blast radius of a conflict small, with guidance to keep client clocks tightly synced or use operations that aren't order-sensitive (counters, sets).

</QA>

<QA q="What limits the use of vector clocks in practice?" level="hard">

The vector has one entry per writer, so it grows with the number of distinct writer processes. Pruning entries for decommissioned processes keeps it manageable, but with **unbounded writers** (e.g., many clients writing directly) the vector is unbounded too — the reason Cassandra didn't adopt them.

</QA>

<QA q="How does Spanner achieve global strict serializability?" level="hard">

**TrueTime**: atomic clocks plus GPS bound clock uncertainty to a few ms (1–7 ms per the 2012 paper), and the API returns time as `[earliest, latest]`. On commit, Spanner picks timestamp `t` and **waits** until `t` is less than `TrueTime.now().earliest` before returning — so no later transaction can get a lower timestamp. With Paxos replication, this gives external consistency. Cross-shard transactions still use 2PC, but over Paxos-replicated participants, so one machine failure doesn't block them.

</QA>

<QA q="HLC vs TrueTime — what do you give up by not having atomic clocks?" level="hard">

TrueTime needs hardware (atomic clocks + GPS in every DC) but provides a tight, known uncertainty bound that commit-wait can use for strict serializability. HLC needs only ordinary clock sync (NTP) and gets much of the benefit — causal ordering plus near-physical timestamps — but its guarantees are slightly weaker, and it assumes clocks stay within a skew bound; far-apart clocks degrade its physical fidelity.

</QA>

<QA q="Design conflict resolution for a multi-region eventually consistent KV store." level="scenario">

- **Version vectors per key**: detect conflicts; on read, return all concurrent versions and let the app merge.
- **HLC + CRDTs**: commutative types (G-counter, OR-set, LWW-register on HLC) so no conflict detection is needed.
- **App-level resolver hook**: default to LWW on HLC.

For a new design: HLC + CRDTs where the data semantics allow, explicit conflict resolution for the rest.

</QA>

<QA q="A tracing system orders spans by local timestamps and sometimes shows children before parents. Fix?" level="scenario">

The cause is clock skew between services: a child span on service B can carry an earlier timestamp than its parent on service A even though B's work came after. Fixes: order spans by the **parent-child tree** that trace propagation already carries and use timestamps only for durations (what Jaeger and Zipkin do, plus skew adjustment in the UI), or attach logical/HLC timestamps to the span context and order by those.

</QA>

</Practice>

## TL;DR cheat sheet

- Wall-clock time is unreliable across distributed nodes.
- **Lamport**: 1 counter per process; ensures causality but hides concurrency.
- **Vector clocks**: 1 counter per process; can detect concurrent vs ordered. Grows with process count.
- **HLC** (Hybrid Logical Clock): (physical, logical) pair. Close to wall-clock + causally correct. Used by CockroachDB, MongoDB.
- **TrueTime** (Spanner): atomic-clock-backed time intervals; enables strict serializability.
- Use version vectors per object for conflict detection in eventually consistent KVs.
- For LWW, prefer HLC over wall-clock.
