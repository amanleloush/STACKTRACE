## Definition (interview-ready)

**Cassandra** is a leaderless, eventually consistent, wide-column distributed database optimized for very high write throughput. Data is partitioned by a **partition key** (hashed onto a token ring), ordered within partitions by **clustering keys**, replicated to N nodes, and queried with tunable consistency. **ScyllaDB** is a high-performance reimplementation in C++ with the same data model (Cassandra-compatible CQL) and dramatically better latency/throughput per node.

## Why it matters

When write rates dwarf any single Postgres or MySQL machine, when you need linear horizontal scale, when you can model around the access pattern (no joins, denormalize for reads), Cassandra/Scylla is the canonical choice. Time-series, event logs, IoT data, messaging history, recommendation features — all classic fits.

## Core concepts

### Wide-column data model

- **Keyspace** → **Table** → **Rows** keyed by `(partition_key, clustering_key)`.
- A **partition** is the unit of locality — all rows with the same partition key live on the same nodes.
- Within a partition, rows are stored sorted by clustering key.
- "Wide" = a single partition can hold many rows (millions, even).

```cql
CREATE TABLE messages (
  channel_id uuid,
  message_id timeuuid,
  user_id uuid,
  body text,
  PRIMARY KEY ((channel_id), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```
- `channel_id` is the partition key — all messages for a channel live together.
- `message_id` is the clustering key, sorted descending — newest first, fast `LIMIT 50` queries.

### Storage: LSM trees

- Writes append to a **commit log** (durability) and **memtable** (in-memory sorted structure).
- Memtable flushes to **SSTable** (immutable sorted file on disk).
- Background **compaction** merges SSTables — choices: STCS (size-tiered), LCS (leveled), TWCS (time-window). Critical tuning for performance.
- Writes are very fast; reads must check multiple SSTables + memtable, with **bloom filters** + **partition index** to prune.

### Token ring & consistent hashing

- Hash the partition key → token (Murmur3, 64-bit).
- Each node owns a range of tokens (or many small ranges via vnodes).
- Default `num_tokens`: 256 vnodes per node before Cassandra 4.0; 16 since 4.0 (paired with the token-allocation algorithm to keep distribution even).

### Replication

- **Replication factor (RF)**: how many copies. Common: 3.
- Replication topology: **NetworkTopologyStrategy** specifies replicas per DC for multi-DC clusters.
- Every node knows the ring; clients can be **token-aware** to send writes directly to a replica (skip an extra hop).

### Tunable consistency (CL — consistency level)

For each read or write, choose how many replicas must respond:
- `ONE`, `TWO`, `THREE`, `QUORUM`, `ALL`, `LOCAL_QUORUM` (just this DC), `EACH_QUORUM` (quorum in every DC).

**Quorum**: `floor(RF/2) + 1`. With RF=3, QUORUM = 2.

**Strong consistency rule of thumb**: `R + W > RF`. So with RF=3, W=2 and R=2 means writes and reads overlap on at least one node → you'll see your write.

### Hinted handoff & read repair

When a write target is down, the coordinator stores a **hint** and replays it when the target returns. **Read repair** detects divergence at read time and reconciles. Background **anti-entropy** repair (`nodetool repair`) merges differences periodically.

### Gossip

Nodes exchange state with a few peers each second, propagating cluster membership and node health epidemically. No central master. Within seconds the whole cluster converges on a consistent view.

### Tombstones

Deletes are **tombstones** (markers, not in-place removals). Compaction physically removes them after `gc_grace_seconds` (default 10 days, so anti-entropy can converge). Heavy delete + read patterns can pile tombstones and slow scans dramatically.

### Lightweight Transactions (LWT)

Cassandra `IF` clauses (`UPDATE ... IF status = 'OPEN'`) use **Paxos**. Strong consistency for single partition, but classic Paxos needs **4 round trips** between coordinator and replicas (Cassandra 4.1's Paxos v2 trims this) — much slower than normal writes. Use only when you must.

### Scylla differences

- C++, shard-per-core architecture (no shared state across cores) — saturates modern hardware.
- Same CQL protocol and data model.
- ScyllaDB's own benchmarks claim several-fold (up to ~10×) throughput vs Cassandra on the same hardware.
- Better tail latency.
- Drop-in for Cassandra clients in most cases.

## How it works (a write at QUORUM, RF=3)

```
Client → Coordinator (any node, ideally token-aware)
  Coordinator forwards write to all 3 replicas
  Each replica: commit log + memtable
  When 2 of 3 ack → write returns to client
  3rd may lag; hinted handoff if it was down
```

## Real-world examples

- **Instagram**: feed timeline storage (huge write throughput).
- **Discord**: messages — migrated from MongoDB → Cassandra → **ScyllaDB**. Wrote a great blog on why.
- **Netflix**: countless services on Cassandra (watch history, customer events).
- **Apple**: famously runs huge Cassandra clusters (75,000+ nodes and 10+ PB as of its 2014 disclosure).
- **eBay, Uber, Spotify**: heavy Cassandra users for various workloads.

## Common pitfalls

- **Unbounded partition growth**: `PARTITION KEY = user_id` and a user with 100M events → one node carrying 50 GB of one partition → GC pauses, slow reads. Bucket the partition (`(user_id, day)`).
- **`ALLOW FILTERING`**: forces scatter-gather across all nodes — production-killer. Treat it as a code-review red flag.
- **Tombstone-heavy reads**: deleting many rows then querying the same partition → query scans tombstones. Reshape to TTL or time-bucket partitions.
- **Read-modify-write**: at default consistency, lost updates. Use LWT (slow) or CRDT-style commutative writes (counter, set).
- **Joining at the application layer**: bad fit for Cassandra. Denormalize at write time.
- **Choosing Cassandra for low-write OLTP**: massive operational overhead vs Postgres.

## Practice questions

<Practice>

<QA q="What's a partition key vs a clustering key?" level="easy">

The **partition key** is hashed (Murmur3) onto the token ring and decides which nodes store the row. All rows with the same partition key live together. The **clustering key** decides the sort order of rows within a partition. Together they form the primary key: `PRIMARY KEY ((partition), clustering)`.

</QA>

<QA q="Why is Cassandra eventually consistent?" level="easy">

It's leaderless: writes go to several replicas and only some need to acknowledge, so replicas can diverge for a while. Consistency is **tunable per operation**. If reads and writes overlap (`R + W > RF`) you get strong consistency for those operations, while lower levels like `ONE` trade it for latency and availability.

</QA>

<QA q="Why is `ALLOW FILTERING` a red flag in Cassandra?" level="easy">

It lets a query filter on columns that aren't part of the partition key, which forces a scatter-gather scan across nodes and partitions instead of a direct lookup. Fine on a tiny table, a production-killer at scale. The fix is to model a table for that access pattern (denormalize at write time).

</QA>

<QA q="How do Cassandra nodes know about cluster membership without a master?" level="easy">

**Gossip**: each node exchanges state with a few peers every second, and membership and health information spreads epidemically. Within seconds the whole cluster converges on the same view, with no central master. Clients can also be **token-aware** and send each request straight to a replica, skipping an extra coordinator hop.

</QA>

<QA q="Explain the rule `R + W` greater than `RF`." level="medium">

With replication factor RF, if a write is acknowledged by W replicas and a read consults R replicas, `R + W > RF` guarantees the two sets overlap in at least one replica that has the latest write. With RF=3, QUORUM = `floor(3/2) + 1` = 2, so W=2 and R=2 gives 4 > 3: read-your-writes consistency.

</QA>

<QA q="How does Cassandra detect and repair divergence between replicas?" level="medium">

1. **Hinted handoff**: the coordinator stores writes meant for a down node and replays them when it returns.
2. **Read repair**: when replica responses disagree on a read, the coordinator picks the newest value and writes it back to the stale replicas.
3. **Anti-entropy repair** (`nodetool repair`): periodic Merkle-tree comparison across replicas that syncs the differences. It must run within `gc_grace_seconds`, or deleted data can come back.

</QA>

<QA q="Why do tombstones cause problems?" level="medium">

Deletes write a marker (a tombstone) instead of removing data, and compaction only purges it after `gc_grace_seconds` (10 days by default). Reads have to skip tombstones, so heavy deletes plus range scans mean scanning thousands of tombstones per query: slow reads and memory pressure. Mitigate with TTL-based expiry, time-bucketed partitions, and TWCS compaction.

</QA>

<QA q="What are the main compaction strategies and when do you use each?" level="medium">

Compaction merges immutable SSTables in the background.

- **STCS** (size-tiered): merges SSTables of similar size. Cheap on write-heavy workloads, but a partition can be spread across many SSTables.
- **LCS** (leveled): keeps data in levels of non-overlapping SSTables, so reads touch few files. Better for read-heavy or update-heavy tables, at the cost of more compaction I/O.
- **TWCS** (time-window): groups SSTables by time window. Ideal for time series with TTLs, because whole windows expire together.

</QA>

<QA q="What are lightweight transactions and why should you use them sparingly?" level="hard">

LWTs are conditional writes (`INSERT ... IF NOT EXISTS`, `UPDATE ... IF status = 'OPEN'`) implemented with **Paxos**, which gives compare-and-set semantics within a single partition. Classic Paxos needs about **4 round trips** between the coordinator and replicas (Cassandra 4.1's Paxos v2 trims this), so LWTs are much slower than normal writes. Use them only where you truly need uniqueness or check-then-set. Otherwise prefer idempotent or commutative writes (counters, sets).

</QA>

<QA q="Why did Discord migrate from Cassandra to ScyllaDB?" level="hard">

Cassandra's JVM garbage-collection pauses caused p99 spikes, and Discord's messaging needed predictable latency at huge scale. Scylla's shard-per-core C++ design has no GC. They went from 177 Cassandra nodes to 72 Scylla nodes; p99 historical-read latency dropped from 40–125 ms to ~15 ms, and p99 inserts from 5–70 ms to a steady ~5 ms. CQL compatibility meant minimal application changes.

</QA>

<QA q="Design a Cassandra schema for a chat app with users, channels and messages." level="scenario">

```cql
CREATE TABLE messages_by_channel (
  channel_id uuid,
  bucket_day text,           -- e.g. '2026-05-29', bounds partition size
  message_id timeuuid,
  user_id uuid,
  body text,
  PRIMARY KEY ((channel_id, bucket_day), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

Bucketing by day bounds partition size. Newest-first clustering makes "last 50 messages" a fast slice. For "all messages by a user", write a second denormalized table keyed by `user_id`. Query-first modeling with no joins.

</QA>

<QA q="One node in a Cassandra cluster has 3x the load of the others. Why?" level="scenario">

- **Hot partition**: one celebrity user's or tenant's partition pinned to that node's token range. Mitigate by bucketing the partition key.
- **Uneven token ranges**: too few vnodes, or a node bootstrapped with bad tokens.
- **Hardware variance**: an older box or slower disks.
- **Compaction backlog** eating CPU and I/O. Check `nodetool compactionstats`.

</QA>

<QA q="Reads for some users have become slow and the GC log on one node shows long pauses. The table is keyed by `user_id` and stores every event a user generates. What's wrong and how do you fix it?" level="scenario">

The partitions are **unbounded**: heavy users accumulate millions of events in a single partition (tens of GB on one replica set), which causes huge reads, GC pressure and slow compaction. Fix by bucketing the partition key, e.g. `((user_id, day), event_time)`, so each partition stays bounded, and query the buckets you need. If old events expire, add a TTL and use TWCS. Migrate by dual-writing to the new table and backfilling.

</QA>

</Practice>

## Quiz

<Quiz>

<MCQ q="With RF=3, which read/write consistency combination guarantees a read sees the latest acknowledged write?" options={["W=ONE, R=ONE", "W=ONE, R=TWO", "W=QUORUM, R=QUORUM", "W=TWO, R=ONE"]} answer={2}>

QUORUM is 2 with RF=3, so 2 + 2 = 4 > 3 guarantees overlap. The other combinations sum to 2 or 3, which is not greater than RF, so a read can miss the replica holding the write.

</MCQ>

<MCQ q="In PRIMARY KEY ((channel_id), message_id), what does message_id determine?" options={["Which node stores the row", "The replication factor", "The compaction strategy", "The sort order of rows within the channel partition"]} answer={3}>

channel_id is the partition key, which the token ring uses for placement. message_id is the clustering key, which orders rows inside the partition. Replication and compaction are table or keyspace settings.

</MCQ>

<MCQ q="A team deletes many rows and then runs range scans over the same partitions. Reads get slower and slower. Why?" options={["Deletes write tombstones that reads must scan until compaction purges them after gc_grace_seconds", "Deletes trigger a full repair on every read", "Bloom filters are disabled after deletes", "Deleted rows are moved to a slower disk tier"]} answer={0}>

Tombstones are markers, not physical removals, and range scans wade through them. Bloom filters and repair aren't what slows these reads down.

</MCQ>

<MCQ q="Why must nodetool repair run more often than gc_grace_seconds?" options={["Otherwise hinted handoff is disabled", "Otherwise a replica that missed a delete can resurrect the data after the tombstone is purged elsewhere", "Otherwise the commit log fills the disk", "Otherwise gossip stops propagating membership"]} answer={1}>

If tombstones are compacted away before every replica learns about the delete, the stale replica's copy looks live and repair spreads it back. That's the reason for the default 10-day grace period.

</MCQ>

<MCQ q="Which compaction strategy fits an IoT time-series table where every row has a 30-day TTL?" options={["Size-tiered (STCS)", "Leveled (LCS)", "No compaction", "Time-window (TWCS)"]} answer={3}>

TWCS groups data by time window, so whole SSTables expire together and are dropped cheaply. STCS and LCS mix old and new data, leaving expired rows scattered across files.

</MCQ>

<MCQ q="You need a unique username constraint in Cassandra. What is the appropriate tool, and its cost?" options={["A lightweight transaction (INSERT IF NOT EXISTS) using Paxos, which costs several extra round trips", "A secondary index, which is free", "Consistency level ALL on a normal insert, which guarantees uniqueness", "ALLOW FILTERING on a read before the insert"]} answer={0}>

Only Paxos-based LWTs give compare-and-set semantics. A read-then-write, even at ALL, can race with a concurrent insert, and ALLOW FILTERING just adds a full scan.

</MCQ>

<MCQ q="A query uses ALLOW FILTERING on a non-key column in a 2-billion-row table. What happens?" options={["The query uses a bloom filter and returns instantly", "Cassandra automatically creates an index", "The query scatters across nodes and scans far more data than it returns", "The query is rejected at parse time"]} answer={2}>

ALLOW FILTERING explicitly permits an inefficient scan, which hurts at scale. Cassandra doesn't auto-index, and the clause is what lets the query run instead of being rejected.

</MCQ>

<MCQ q="What was the main driver of Discord's move from Cassandra to ScyllaDB?" options={["Cassandra lacked CQL support", "Unpredictable tail latency from JVM garbage-collection pauses", "Scylla supports multi-row ACID joins", "Cassandra cannot replicate across datacenters"]} answer={1}>

GC pauses produced p99 spikes, and Scylla's C++ shard-per-core design avoids GC entirely. Both use CQL and support multi-DC replication, and neither offers joins.

</MCQ>

</Quiz>

## TL;DR cheat sheet

- Wide-column data model: `((partition), clustering)` primary key.
- LSM tree storage: memtable → SSTables → compaction.
- Token ring + consistent hashing + vnodes. RF copies per partition.
- Tunable consistency per operation. `R + W > RF` for strong.
- Reads: bloom filters + partition index + SSTable scan + merge.
- Tombstones live `gc_grace_seconds` (10 days default). Repair before that.
- Avoid: unbounded partitions, `ALLOW FILTERING`, read-modify-write at low consistency, joins.
- Scylla: same model, C++ + shard-per-core → much higher throughput.
