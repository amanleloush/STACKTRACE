## Definition (interview-ready)

**Replication** copies the same data to multiple nodes for read scaling, durability, and HA — synchronous (strong consistency, slower writes) or asynchronous (fast writes, possible loss). **Sharding** (a.k.a. partitioning) splits a dataset across nodes so each holds a subset — for write scaling and storage scaling.

## Why it matters

You hit replication when reads outgrow one machine (most apps); you hit sharding when writes or storage outgrow one machine (fewer, but harder). Choosing replication topology and shard key sets the upper bound on your scale and most of your operational pain.

## Core concepts

### Replication topologies

- **Single-leader (primary/replica)**: writes to one leader, asynchronous (or sync) replication to replicas. Reads can hit replicas for scale. Failure of leader → promote a replica (auto or manual).
- **Multi-leader**: multiple leaders accept writes, replicate to each other. Useful across regions. Requires conflict resolution (last-write-wins, CRDTs, application logic).
- **Leaderless**: any node accepts writes, writes go to W replicas, reads from R. Requires read-repair, anti-entropy. Used by Cassandra, Riak, and Amazon's original Dynamo (not DynamoDB, which uses a leader per partition).

### Sync vs async replication

- **Sync**: leader doesn't ack until N replicas confirm. Stronger durability; commit latency = slowest replica's RTT.
- **Async**: leader acks immediately. Faster, but on crash you can lose unreplicated writes — that's your **RPO** (recovery point objective).
- **Semi-sync** (MySQL): wait for at least one replica to receive (not apply) the write before ack — middle ground.

### Replication lag

Async replicas trail the leader by some time (ms to seconds, occasionally minutes under load).

Consequence patterns:
- **Read-your-writes**: user writes → reads from a replica before the write propagates → "where did my comment go?" Fixes: route to leader for read after write, sticky session, or read from "self" only via leader.
- **Monotonic reads**: user reads from replica A (sees v1), next read from replica B (sees v0). Fix: sticky to one replica.
- **Causal consistency**: comment B references comment A; both must be visible in order. Fix: causal tracking, or single-leader for write chains.

### Failover

- Detect leader failure (heartbeat).
- Pick a new leader (the most up-to-date replica).
- Reconfigure clients.
- Old leader rejoins as replica (may need to discard unreplicated writes — **split-brain risk** if not handled).

Tools: AWS RDS Multi-AZ, PgBouncer + repmgr/Patroni for Postgres, Orchestrator for MySQL, Cloud SQL HA.

### Sharding (partitioning) strategies

- **Range partitioning**: shard by key range. `users` with id 1–1M on shard A, 1M–2M on B. Easy range scans. **Hot shards** if writes are monotonic (everyone writes to "latest").
- **Hash partitioning**: shard by `hash(key) % N`. Evenly spreads load. Loses range-scan locality. Adding nodes remaps almost everything → **consistent hashing** to mitigate.
- **Directory-based**: a lookup service maps key → shard. Flexible, but the lookup is a new single point.
- **Geo / locality**: shard by region. Best for user-locality apps.

### Shard key choice

The single most consequential database decision in a sharded system. A good shard key:
- Is in **every query's WHERE clause** (avoid scatter-gather across shards).
- Has **high cardinality** (millions of distinct values, not 5).
- Has **balanced access** (no celebrity user generating 10% of traffic).
- Lets you **localize transactions** to a single shard (no cross-shard ACID).

Real-world: tenant ID, user ID, customer ID are common. Time is a frequent **anti-pattern** (recent shard becomes hot).

### Cross-shard operations

- **Cross-shard joins**: scatter-gather, slow.
- **Cross-shard transactions**: need 2PC (expensive, partial-failure modes) or sagas (eventual).
- **Aggregations**: each shard computes locally, coordinator merges.
- **Global secondary indexes**: index materialized across shards (DynamoDB GSI, Vitess).

### Rebalancing

- Adding a shard: with hash sharding and `% N`, almost all keys remap. **Use consistent hashing** / vnodes (Cassandra, Riak) or splittable ranges over a hashed keyspace (Vitess).
- Tools split shards online (Vitess Reshard, MongoDB chunk migration).

```
Client                          Router/Proxy                Shard

  |                             |-------------------------->|
  |                             |<-- rows -----------------|
  |<------ rows ---------------|                           |
```

## Real-world examples

- **YouTube → Vitess**: sharded MySQL with online resharding, query routing, transparent to apps.
- **Uber → Schemaless**: append-only key-value store layered on sharded MySQL (rows keyed by UUID, e.g., a trip ID); each storage cluster is a MySQL master with minion replicas.
- **Discord**: messages sharded by channel ID over Cassandra (now ScyllaDB) — channel = unit of locality.
- **Stripe**: runs its own sharded document database (DocDB, built on MongoDB) and moves data between shards online with zero-downtime migrations.
- **MongoDB / Cassandra / DynamoDB**: sharding is built-in.

## Common pitfalls

- **Picking a low-cardinality shard key** (e.g., `country`) → 5 countries = 5 shards forever, hot ones unmanageable.
- **Time as shard key** → all writes to today's shard.
- **Cross-shard joins**: slow, fragile. Denormalize or use a query layer.
- **Forgetting to replicate the WAL**: replicas built from snapshots only → recovery gap.
- **Replication lag during a deploy**: long-running migration backs up the replication stream. Use online schema change tools.
- **Failover during a network partition**: two nodes both think they're leader → **split brain**, divergent data. Use fencing (STONITH), majority quorum, or hosted HA.
- **Read-after-write surprises**: API returns 200 OK, user refresh shows old data. Route critical follow-up reads to leader.

## Practice questions

<Practice>

<QA q="When do you replicate vs shard?" level="easy">

Replicate when **reads** outgrow one node, or for HA/durability. Shard when **writes or storage** outgrow one node. They're complementary — most large systems do both.

</QA>

<QA q="What is replication lag and why does it matter?" level="easy">

The delay between a write committing on the leader and being applied on a replica. It matters because users who write and then read from a replica may not see their own write — a **read-your-writes** violation.

</QA>

<QA q="Compare single-leader, multi-leader, and leaderless replication." level="easy">

- **Single-leader**: all writes go to one leader, which replicates to replicas; reads can be spread across replicas. Simplest; failover means promoting a replica.
- **Multi-leader**: several leaders accept writes and replicate to each other — useful across regions, but concurrent writes conflict and need resolution (last-write-wins, CRDTs, application logic).
- **Leaderless**: any node accepts writes; a write goes to W replicas and a read queries R. Needs read-repair and anti-entropy. Used by Cassandra, Riak, and Amazon's original Dynamo (not DynamoDB, which has a leader per partition).

</QA>

<QA q="How would you pick a shard key for an e-commerce orders table?" level="medium">

Likely `customer_id` (or `merchant_id`, depending on the access pattern). It has high cardinality, appears in most queries, and is balanced (no single customer dominates). Time alone (`created_at`) would be terrible because today's shard takes all the writes.

</QA>

<QA q="Compare sync and async replication tradeoffs." level="medium">

**Sync**: stronger durability (the write isn't acked until replicas confirm) but higher write latency, gated by the slowest replica. **Async**: low latency, but on a leader crash you lose unreplicated writes (RPO greater than 0). Many setups use **semi-sync** — wait for at least one replica to receive (not apply) the write before acking.

</QA>

<QA q="A user refreshes a page twice and sees newer data, then older data. What happened and how do you fix it?" level="medium">

A **monotonic reads** violation: the first read hit a replica that had caught up (saw v1), the second hit a more-lagged replica (saw v0), so time appeared to go backwards. Fix by making each user's reads **sticky to one replica** (e.g., route by a hash of the user ID), so they never move to a replica that's further behind.

</QA>

<QA q="Compare range and hash partitioning." level="medium">

- **Range**: shard by key range (ids 1–1M on A, 1M–2M on B). Range scans stay on one shard, but monotonic keys (ids, timestamps) send all new writes to the last shard — a **hot shard**.
- **Hash**: shard by `hash(key) % N`. Spreads load evenly but loses range-scan locality, and with plain modulo, changing N remaps almost every key — hence consistent hashing or splittable ranges over a hashed keyspace.

</QA>

<QA q="How does consistent hashing help when adding shards?" level="medium">

With `hash(key) % N`, adding a shard remaps almost all keys (massive data movement). Consistent hashing places nodes on a ring; adding one moves only about 1/N of the keys (the ones that now fall to the new node). Critical for online rebalancing of caches and KV stores.

</QA>

<QA q="How are queries that span shards handled — joins, aggregations, and lookups by a non-shard-key column?" level="hard">

- **Joins**: scatter-gather across shards — slow and fragile, so most teams denormalize or co-locate related rows under the same shard key.
- **Aggregations**: each shard computes a partial result locally; a coordinator merges them.
- **Lookups by another column**: without help this is a query to every shard. A **global secondary index** — an index materialized across shards (DynamoDB GSI, Vitess) — routes it to the right place.

</QA>

<QA q="What is split brain and how do you prevent it?" level="hard">

During a network partition, two nodes both believe they're the leader and both accept writes, so the data diverges. Prevent it with a **majority quorum** for leader election (only one side can have a majority), **fencing** the old leader (STONITH, firewall rules) so it can't accept writes, or a hosted HA service that does both.

</QA>

<QA q="A sharded MySQL setup needs a transaction across two shards. What are your options?" level="scenario">

1. **Two-phase commit**: slow and fragile (prepare then commit; coordinator failure leaves locks held).
2. **Saga**: break the work into compensable local transactions, coordinated by an orchestrator or by choreography.
3. **Re-shard**: pick a key that keeps the transaction local (e.g., put both records under the same tenant).
4. **Outbox + idempotent retry**: record the intent on shard A; an async process picks it up and applies it on B.

Most teams choose (3) or (4).

</QA>

<QA q="Production setup: 1 leader, 3 async replicas. The leader crashes. How do you fail over safely?" level="scenario">

- Detect failure via consensus — don't fail over on a single missed heartbeat.
- Among the replicas, pick the **most up-to-date** one (highest WAL position / GTID).
- Promote it and reconfigure clients (DNS, proxy, etcd).
- When the old leader returns it may hold **unreplicated writes** — discard them (ideally logging them) to avoid divergence. This is data loss; that's the cost of async.
- Fence the old leader (firewall, STONITH) until you're sure it won't accept writes.

</QA>

<QA q="Re-shard a 10 TB Postgres on `tenant_id` to add capacity, with zero downtime. Approach?" level="scenario">

- Double-write to old and new for a transition period.
- Backfill historical data into the new shard (chunked, throttled).
- Cut reads over once the new shard is verified consistent.
- Stop double-writing and decommission the moved slice of the old shard.
- Tools: logical replication (pglogical), Debezium for CDC, Citus for native sharding.

The hardest part is **invariants that cross shards** — those need application-level handling first.

</QA>

</Practice>

## Quiz

<Quiz>

<MCQ q="Your app's reads have outgrown one database node but writes are modest. What is the usual first step?" options={["Shard by user ID", "Add read replicas", "Switch to multi-leader replication", "Partition by created_at"]} answer={1}>

Replication scales reads; sharding is for when writes or storage outgrow one node. Multi-leader adds conflict resolution for no benefit here, and time-based partitioning creates a hot shard.

</MCQ>

<MCQ q="With asynchronous replication, what does a leader crash risk?" options={["Higher write latency on every commit", "Losing writes that were acked but not yet replicated", "Replicas rejecting reads permanently", "Automatic split brain on every failover"]} answer={1}>

Async acks before replicas confirm, so acked writes not yet shipped are lost on a crash (RPO greater than 0). Higher commit latency is the cost of sync replication, not async.

</MCQ>

<MCQ q="What does MySQL semi-sync replication wait for before acknowledging a commit?" options={["All replicas to apply the write", "No replicas at all", "A majority of replicas to apply the write", "At least one replica to receive the write"]} answer={3}>

Semi-sync waits for at least one replica to receive (not apply) the write — a middle ground between async speed and sync durability.

</MCQ>

<MCQ q="Which shard key is the worst choice for a high-write orders table?" options={["created_at", "customer_id", "merchant_id", "order_id hashed"]} answer={0}>

Time is the classic anti-pattern: every new order lands on the current shard, making it hot while others sit idle. The ID-based keys have high cardinality and spread writes.

</MCQ>

<MCQ q="A cluster uses hash(key) % N with 8 shards. Why is adding a 9th shard painful?" options={["Hash functions cannot handle 9 buckets", "Range scans stop working", "Almost every key maps to a different shard and must move", "Only the new shard receives writes afterward"]} answer={2}>

Changing N changes the modulo result for nearly every key. Consistent hashing (or splittable ranges over a hashed keyspace) limits movement to roughly 1/N of the keys.

</MCQ>

<MCQ q="A user posts a comment, refreshes, and the comment is missing. Which fix targets this directly?" options={["Add more async replicas", "Route that user's reads right after a write to the leader", "Switch from hash to range partitioning", "Increase the replica heartbeat interval"]} answer={1}>

This is a read-your-writes violation from replication lag. Reading from the leader (or a sticky, caught-up path) right after a write fixes it; the other options don't affect lag visibility.

</MCQ>

<MCQ q="During failover after a leader crash, which replica should be promoted?" options={["The one with the lowest load", "The one in the same AZ as most clients", "A random replica to avoid bias", "The most up-to-date one, by highest WAL position or GTID"]} answer={3}>

Promoting the replica furthest ahead minimizes lost writes. Load or locality matter less than not discarding data that a more caught-up replica already has.

</MCQ>

<MCQ q="Which mechanism prevents two nodes from both acting as leader during a network partition?" options={["Majority quorum for election plus fencing the old leader", "Shorter TTLs on DNS records", "Switching to async replication", "Adding read replicas in each region"]} answer={0}>

Only one side of a partition can hold a majority, and fencing (STONITH, firewall) stops the old leader from accepting writes. DNS TTLs and extra replicas don't stop a stale leader from writing.

</MCQ>

<MCQ q="A query filters orders by product_id, but the table is sharded by customer_id. Without extra structures, what happens?" options={["It routes to one shard by hashing product_id", "It is rejected by the router", "It must scatter to every shard and merge results", "It reads only from the leader shard"]} answer={2}>

The router can only target a shard when the shard key is in the WHERE clause. Otherwise it scatter-gathers; a global secondary index on product_id avoids that.

</MCQ>

</Quiz>

## TL;DR cheat sheet

- **Replication** = redundancy + read scaling. Sync (safe, slow) vs Async (fast, lossy).
- **Replication lag** breaks read-your-writes; route critical reads to leader.
- **Sharding** = horizontal write/storage scaling. Choose: range, hash, directory, geo.
- **Shard key** must have high cardinality, balanced load, and appear in most queries.
- Time as a shard key is a famous anti-pattern.
- Cross-shard joins/transactions are expensive — prefer locality or sagas.
- Consistent hashing minimizes data movement on rebalance.
- Split brain: prevent with quorum + fencing.
