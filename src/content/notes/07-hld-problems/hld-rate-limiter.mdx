## Problem statement

Design a rate limiter that enforces request quotas per user/API key across many app servers and regions, returning `429 Too Many Requests` when exceeded, with low latency.

<Anim id="bucket" />

<Anim id="rate-window" />

## Requirements

### Functional
- Per-key limits (user, API key, IP).
- Multiple tiers (free 100/min, pro 1K/min, enterprise 10K/min).
- Returns 429 + `Retry-After`.
- Optionally: per-endpoint limits, per-time-window quotas.

### Non-functional
- Latency overhead < 5 ms per request (ideally < 2 ms).
- Available — never fail open silently, never fail closed entirely.
- Accurate enough — small over/under-limit acceptable (≤ 1% drift).
- Multi-region with low cross-region traffic.

## Scale estimation

- 1M QPS across the platform.
- Each request consumes one rate-limit check.
- 100M unique keys (users + API keys).
- State per key: ~50 bytes → 5 GB. Fits in memory.

## High-level architecture

```
                   ┌────────────┐
       Client ──►  │ API Gateway│ ──► App Tier
                   └─────┬──────┘
                         ▼
                   ┌──────────────┐
                   │ Rate Limiter │
                   │   sidecar    │
                   └──────┬───────┘
                          ▼
                   ┌──────────────┐
                   │ Redis (Lua)  │ ──► (optional Kafka)
                   └──────────────┘
```

Two placement choices:
- **Gateway-level**: cheap, global view, but extra network hop.
- **Per-service / sidecar**: closer to the call; one Redis op per request.

Most production setups use **gateway-level for ingress + per-service for sensitive endpoints**.

## Algorithm choice

**Token bucket** (recommended):
- Allows controlled bursting (UX-friendly).
- O(1) per check via Lua script.
- See [Rate Limiting](/learn/notes/rate-limiting/).

For exact limits, sliding-window counter is the next choice.

## Detailed design

### Lua-script rate limit (token bucket)

```lua
-- KEYS[1] = rl:user42
-- ARGV: now_ms, refill_rate (per ms), capacity
local b = redis.call("HMGET", KEYS[1], "tokens", "ts")
local tokens = tonumber(b[1]) or tonumber(ARGV[3])
local ts = tonumber(b[2]) or tonumber(ARGV[1])
local elapsed = tonumber(ARGV[1]) - ts
tokens = math.min(tonumber(ARGV[3]), tokens + elapsed * tonumber(ARGV[2]))
local ok = 0
if tokens >= 1 then
  tokens = tokens - 1
  ok = 1
end
redis.call("HSET", KEYS[1], "tokens", tokens, "ts", ARGV[1])  -- HMSET is deprecated since Redis 4.0
redis.call("EXPIRE", KEYS[1], 600)
return ok
```

One round-trip, atomic, ~1 ms.

### Plan lookup

- Plans table (small) cached in memory at app boot, refreshed every N minutes.
- Key → plan resolved before the Redis call.

### HTTP response

```
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1716985260
Content-Type: application/json

{ "error": "rate_limit_exceeded", "retry_after": 30 }
```

### Multi-tier limits

- Per-user: 1000/min.
- Per-endpoint family: 100/min on `/search`.
- Per-IP fallback (for unauthenticated traffic).
- Each tier = separate Redis key; all must allow → request passes.

```
allowed = all([
  rate_limit("user:42", per_user_limit),
  rate_limit("endpoint:search:user:42", per_endpoint_limit),
  rate_limit("ip:1.2.3.4", per_ip_limit),
])
```

### Multi-region strategy

Two approaches:

#### 1. Per-region limits (sum-of-regions ≤ global limit)

- Each region has its own Redis.
- Pro: low latency, simple.
- Con: drift — a user can briefly exceed global limit if traffic is uneven.

Acceptable for most use cases.

#### 2. Global synchronization

- Each region pulls **leases** from a global counter.
- More accurate; more complex.
- Rarely worth it: even Cloudflare counts per data center (an isolated counter per PoP), i.e. approach #1.

Most teams use #1 with conservative per-region caps.

### Failure modes

- **Redis down**: fail open? fail closed?
  - **Fail open**: allow all requests during outage. Risk: protected resource gets overwhelmed.
  - **Fail closed**: reject all. Risk: outage visible to all users.
  - **Practical**: degraded mode — local in-memory token bucket per gateway instance as fallback (no global view, but each instance limits itself).

### Header propagation

For composite rate limits (gateway + service), the gateway can pass `X-RateLimit-Cost` and `X-RateLimit-Plan` headers; downstream services trust the gateway.

## Optimizations

- **In-memory cache + periodic sync**: each gateway instance maintains a local token bucket; periodically syncs with Redis to merge state. Reduces Redis pressure dramatically, at the cost of some accuracy.
- **Batched updates**: instead of every request hitting Redis, batch updates per (key, window). Tradeoff: small accuracy loss.
- **Sliding window counter** instead of token bucket for stricter limits without sacrificing too much accuracy.
- **Sharded Redis by key**: hash key → Redis instance. Linear scaling.

## Trade-offs

- **Strict accuracy vs latency**: cross-region sync = accurate but slow. Per-region = fast but drifts.
- **Token bucket vs sliding window**: token bucket allows bursting (good UX); sliding window is smoother (anti-burst).
- **Fail open vs closed**: matters when Redis fails. Tier-based: fail closed for sensitive APIs, fail open for read-only.
- **Per-IP limiting**: NATs and mobile carriers share IPs — false positives. Combine with user limits.

## Practice questions

<Practice>

<QA q="What should a rate-limited response look like?" level="easy">

`429 Too Many Requests` with a `Retry-After` header telling the client when to try again, plus `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` so well-behaved clients can pace themselves, and a small JSON error body.

</QA>

<QA q="Why is limiting only by IP address risky?" level="easy">

NATs and mobile carriers put many users behind one IP, so one heavy user can get everyone behind that IP blocked (false positives). Use per-IP limits as a fallback for unauthenticated traffic and combine them with per-user or per-API-key limits.

</QA>

<QA q="How would you implement rate limiting in Redis?" level="medium">

Lua script implementing token bucket: read tokens + last refill timestamp, refill based on elapsed time, attempt to consume a token, write back, and set an `EXPIRE` so idle keys disappear. Lua makes it atomic in one Redis round trip; a plain read-then-write from the app would let concurrent requests race and both spend the same token.

</QA>

<QA q="Token bucket vs sliding window counter — when to use each?" level="medium">

Token bucket allows controlled bursting (better UX); sliding window counter is closer to a strict rate. For user-facing APIs, bursting is desirable (a quick rush isn't abuse). For DDoS protection, smoother is better.

</QA>

<QA q="How do multi-tier limits (user, endpoint, IP) combine?" level="medium">

Each tier is a separate Redis key with its own limit, such as 1000/min per user, 100/min per user on `/search`, and a per-IP fallback. A request passes only if every applicable tier allows it. When debugging a 429, find which tier tripped.

</QA>

<QA q="Where should the rate limiter run: gateway or per-service sidecar?" level="medium">

Gateway-level is cheap and has a global view of ingress, at the cost of an extra hop. A per-service sidecar sits close to the call and can protect specific sensitive endpoints. Most production setups do both: gateway limits for ingress, per-service limits for sensitive endpoints, with the gateway passing headers like `X-RateLimit-Plan` downstream.

</QA>

<QA q="What happens when Redis fails?" level="medium">

Options: fail open (let all through, risk overload), fail closed (reject all, visible outage), degraded (per-instance local token bucket as fallback, no global view). Tier responses by endpoint sensitivity: fail open for read paths, fail closed for sensitive write paths.

</QA>

<QA q="How to handle multi-region rate limiting?" level="hard">

Per-region limits with sum-of-regions ≤ global is the most common. Each region operates independently with its own Redis; some drift is accepted when traffic is uneven. For strict global limits, regions pull leases from a global counter (more accurate, more complex, rarely worth it — even Cloudflare counts per data center).

</QA>

<QA q="Design rate limiting for a free/pro/enterprise tiered API." level="hard">

- Plans table mapping user_id → plan (free 100/min, pro 1K/min, enterprise 10K/min).
- Cached in app memory, refreshed every few minutes.
- Per-user token bucket with capacity = limit.
- Refill rate = limit / 60 per second.
- Optional per-endpoint sub-limits for expensive operations (for example 10/min on `/export`).
- 429 + Retry-After + headers.

</QA>

<QA q="A rate limiter adds 5 ms to every request — too much. Optimize." level="scenario">

- Local cache + periodic Redis sync: maintain local state, sync every N ms or every K requests (some accuracy loss).
- Co-locate Redis with the gateway (same DC).
- Batch updates.
- Avoid extra round trips: resolve the plan from the in-memory cache and do the check in a single Lua call.
- Shard Redis by key to spread load.

</QA>

<QA q="Design abuse detection on top of rate limiting." level="scenario">

- Stream all rate-limit events to Kafka.
- Consumer detects patterns: same IP rotating user agents, burst-then-pause, denied requests from known abusers.
- Auto-throttle abusers (lower their tier dynamically) or escalate to the security team.
- WAF rules for known bad signatures.

</QA>

<QA q="User reports being rate-limited when they shouldn't be. Investigate." level="scenario">

- Check actual recent request rate from logs vs the limit.
- Look at all rate-limit tiers (user, endpoint, IP) — which one tripped?
- Clock skew: the script takes `now_ms` from the caller, so app servers with skewed clocks can miscompute refill.
- Plan misconfig: was their plan downgraded, or is the plan cache stale?
- Bug in the Lua script under an edge case (for example very small intervals).
- NAT'd IP shared with an abuser?

</QA>

</Practice>

## Quiz

<Quiz>

<MCQ q="Why run the token-bucket logic as a Lua script inside Redis?" options={["Lua is faster than C", "It makes read-refill-consume-write atomic in one round trip", "Redis can't store hashes otherwise", "It replicates the key to all regions"]} answer={1}>

Redis runs the script atomically, so concurrent requests can't both read the same token count, and it's one network round trip. Lua isn't faster than Redis's C core, hashes work without it, and it does nothing for cross-region replication.

</MCQ>

<MCQ q="A pro user has a 1K/min token bucket. What capacity and refill rate fit?" options={["Capacity 1000, refill about 16.7 tokens per second", "Capacity 60, refill 1000 per second", "Capacity 1, refill 1000 per minute", "Capacity 1000, refill 1000 per second"]} answer={0}>

Capacity equals the limit and refill is limit / 60 per second, about 16.7/s. A capacity of 1 removes bursting, and 1000/s refill would allow 60x the limit.

</MCQ>

<MCQ q="A request is checked against per-user, per-endpoint and per-IP limits. When does it pass?" options={["If any one tier allows it", "If the per-user tier allows it", "Only if every applicable tier allows it", "If at least two tiers allow it"]} answer={2}>

Each tier is a separate key, and the request needs all of them to allow it. Any single tier saying no rejects it.

</MCQ>

<MCQ q="With per-region limits that sum to the global limit, what is the known downside?" options={["Every check needs a cross-region call", "It needs a global lease server", "Requests in one region block another region", "A user with uneven traffic across regions can briefly be limited wrongly or drift from the global limit"]} answer={3}>

Each region counts independently, so uneven traffic causes drift against the global limit. Per-region limits avoid cross-region calls and leases, which belong to the global-sync approach.

</MCQ>

<MCQ q="Redis is down. What is a sensible behavior for a write-heavy payment endpoint versus a read-only catalog endpoint?" options={["Fail open for both", "Fail closed for the payment endpoint, fail open for the catalog", "Fail closed for both", "Fail open for payments, fail closed for the catalog"]} answer={1}>

Sensitive write paths should stay protected, while read-only paths can tolerate being let through. A local per-instance bucket is a further degraded option. Failing everything closed is a visible outage; failing everything open risks overload.

</MCQ>

<MCQ q="Which algorithm suits a user-facing API where short bursts are normal?" options={["Token bucket", "Fixed window with a 1-hour window", "Sliding window log with no burst", "Leaky bucket with zero capacity"]} answer={0}>

Token bucket allows controlled bursts up to its capacity while enforcing the average rate. The others are stricter or, like a long fixed window, allow huge spikes at window edges.

</MCQ>

<MCQ q="Many users on one mobile carrier report 429s at the same time. What is the most likely cause?" options={["The Lua script is not atomic", "Redis memory is full", "A shared carrier NAT IP tripped the per-IP limit", "Their plans were upgraded"]} answer={2}>

Carriers put many users behind one IP, so the per-IP tier fires for all of them. The script is atomic, full memory would cause errors not targeted 429s, and an upgrade raises limits.

</MCQ>

<MCQ q="What does keeping a local token bucket on each gateway with periodic Redis sync trade away?" options={["Availability", "The ability to return 429", "Burst support", "Some accuracy, since instances act on slightly stale shared state"]} answer={3}>

Local state cuts Redis round trips and latency, but instances don't see each other's usage until they sync, so limits can drift. Availability actually improves, and 429s and bursting still work.

</MCQ>

</Quiz>

## TL;DR cheat sheet

- Token bucket in Redis via Lua = single round trip, atomic, ~1 ms.
- Multi-tier: user + endpoint + IP limits combined.
- Multi-region: per-region with sum ≤ global; accept drift.
- Return 429 + `Retry-After` + headers.
- Optimize: local cache + sync, batched updates.
- On Redis failure: tier the fail-open/closed by endpoint sensitivity.
- Pair with abuse detection pipeline.
